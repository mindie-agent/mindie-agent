# LangMem and Mastra: source-based integration assessment

Research date: 2026-10-04. Scope: official source and package metadata, plus the isolated LangMem fake-model probe in [langmem-spike/README.md](langmem-spike/README.md). No real model, private history or product source modification was used. This report addresses a rebuildable title/summary index over complete authorized, redacted reference bodies; it does not turn summaries into verified knowledge.

## Decision

**Use LangMem's functional running-summary interface as the first integration candidate.** The completed spike proves that `summarize_messages` can use the existing Harness through a small `.invoke` adapter and persist `RunningSummary` in the existing SQLite transaction. No new database, graph, service or provider authentication is required. Keep the published dependency in an isolated worker environment and pin the resolved versions.

This is a genuine algorithm replacement: remove the current head/tail selection path for the incremental policy and let LangMem manage threshold selection, old-summary/new-message prompt assembly, summary IDs and returned state. The current candidate has no complete running-summary implementation, so adopting LangMem adds that capability; it would be inaccurate to claim a large existing implementation can immediately be deleted. The remaining mechanical partitioning, authority gates, redaction, Harness process guard, cumulative attempt accounting, transaction/CAS boundary and GitHub outbox have domain guarantees that neither framework replaces.

**Do not describe `Mastra.summarizeConversation` alone as an incremental organizer.** It is a useful standalone summarizer with optional extraction, but its implementation calls the observer with no previous observations and exposes no previous-summary/cursor parameter. Adopting full `ObservationalMemory.observe` would replace more scheduling/state/reflection behavior, while adding the Node/Mastra runtime and a derived storage lifecycle. It is a candidate for a broader Harness migration or comparative quality baseline, not the smaller integration for this Python component.

| Property | LangMem `summarize_messages` | Mastra `summarizeConversation` | Mastra full `ObservationalMemory` |
|---|---|---|---|
| Incremental state | Explicit `RunningSummary` | None in public options | Persisted observations, IDs/time boundaries and reflection generations |
| Model calls | 0 below threshold; normally 1 per trigger | Normally 1; extraction adds a call | Observer batches plus periodic reflection and optional extraction |
| Persistence required | Caller-owned state only | None | Memory storage adapter, e.g. local LibSQL |
| Existing Harness bridge | Python `.invoke` → `AIMessage.content` | Node AI-SDK model bridge/provider | Same, plus storage/lifecycle integration |
| Failure control | Function propagates errors; transport owns retries | Hardcoded eight transient retries in this entry point | Configurable failure policy/retry settings; several substeps |
| Main reduction in custom code | Incremental summary algorithm | Prompt/parser/extraction code | Incremental observation/reflection orchestration |

## LangMem: what can be reused directly

`RunningSummary` contains summary text, a set of summarized IDs and the last summarized ID. `summarize_messages` accepts custom initial/update/final prompts and a token counter. It makes one `model.invoke` call when the selected range is nonempty, otherwise none. Our fake Harness exercised both complete delta batches and cumulative history, JSON serialization of state, and a previous summary in the second prompt without the first batch's original text. [Pinned function and arguments](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/short_term/summarization.py#L331-L348), [model call/state update](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/short_term/summarization.py#L462-L487).

The result is summary text, not our title/summary schema. Avoid a second call by customizing the initial and update prompts, keeping the current Harness output-schema contract, and returning its validated title/summary JSON as `AIMessage.content`. Deterministically parse that JSON for the existing metadata fields; keep the same JSON as `RunningSummary.summary` for the next update. The spike proves the API mechanics with fake JSON. It does not prove that a real model obeys the schema, retains corrections or produces useful retrieval metadata. Preserve flags such as failed, incomplete and later-corrected in the requested metadata contract and evaluate their actual retention.

The main trap is upstream trimming. When the selected range exceeds `max_tokens`, it keeps the end of that range; the returned ID set nevertheless includes the entire original selected range. The spike observed three IDs marked summarized without their messages reaching the model. If trimming cannot produce any valid messages, the implementation warns and falls back to the original range, potentially exceeding the intended window. Also, `max_summary_tokens` is only a budgeting value; it is not passed as a provider output limit. [Trim implementation](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/short_term/summarization.py#L225-L256), [output-limit documentation](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/short_term/summarization.py#L379-L386).

Therefore the adapter must submit complete, truly bounded message batches, reserve room for the previous metadata, fixed prompt and output, and reject an oversized single message or split it with explicit coverage semantics before calling LangMem. Its default counter is approximate. Neither the spike's character counter nor the existing 12 KiB input cap establishes real token cost. The model transport must enforce the output cap and expose measured usage.

Let N be all authorized source tokens, B the complete batch budget, R the previous-summary budget and P fixed prompt overhead. With k≈ceil(N/B) batches, model input is approximately N+k(R+P), plus final residual handling. It avoids repeatedly sending the whole growing history, which approaches quadratic model input across equal increments. It costs more than one 12 KiB head/tail sample, because the middle is actually read. Incremental IDs still accumulate O(number of messages); callers that repeatedly supply the full history incur full-history scans/token counting even when model input is bounded. Delta-only batches worked in the spike, but need explicit caller cursor/idempotency invariants.

The functional API has no durable queue or retry loop. That is useful here: keep our task state, bounded attempt ledger, stage checkpoints and atomic summary/body-version CAS. Do not adopt `LocalReflectionExecutor` as durable execution: it uses an in-process priority queue/thread, so restart loses pending jobs. LangMem's semantic MemoryManager/MemoryStoreManager adds extraction, optional insert/update/delete, retrieval/embedding and a Store abstraction. Those are separate features and do not replace the authorized full-reference-body contract; adding them would expand the scope and invocation count. [Reflection executor](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/reflection.py#L254-L328), [memory extraction manager](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/knowledge/extraction.py).

## Mastra: useful behavior and added responsibilities

`summarizeConversation` is directly usable without a database. However, its public options do not expose previous observations, max retries or an output-budget override; it constructs observer configuration with eight transient retries, abort-on-failure and the default 100,000 output-token ceiling. It calls `observerRunner.call(undefined, messages)`, so repeatedly sending the full growing history remains a repeated full-history summary. Optional structured extraction adds another model generation and its own fallback path. [Standalone entry point](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/summarize.ts#L27-L147), [extraction path](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/extraction-runner.ts#L70-L125).

The retry policy allows up to nine transient attempts with approximately 247 seconds of backoff before request time. The observer separately retries degenerate output once, even when maxRetries is zero. Reflection can run up to four increasingly aggressive compression levels, each subject to transient retries. Usage metadata is useful, but the observer returns the successful/last attempt's usage; it is not a guarantee that every billed failed or discarded attempt is counted. A wrapper deadline and an attempt ledger are still necessary. [Retry implementation](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/retry.ts), [observer retry and usage](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/observer-runner.ts#L331-L448), [reflection levels](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/reflector-runner.ts#L402-L511).

The full `ObservationalMemory.observe` API accepts externally supplied messages and selects unobserved IDs/time ranges, so raw body duplication in its database is not inherently required. It still requires a Memory storage adapter. A local LibSQL file is supported; no central cluster is required. Compared with LangMem's single Python adapter, integrating it means a Node child runtime plus an AI-SDK model bridge (or a separate provider client), stable message IDs/timestamps, storage configuration and cleanup. A custom adapter to our SQLite schema could avoid a second file, but maintaining it is extra code that must be counted honestly. [Observe API](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/observational-memory.ts#L3882-L3980).

Defaults include a 30k message threshold, async buffering beginning at about 6k (20%), and reflection at 40k observation tokens. A 10k `maxTokensPerBatch` groups whole threads for resource batching and is a soft grouping target, not a hard bound on one large thread. Resource batches use parallel calls; structured extractors can add calls per thread. Previous-observation context defaults to the last 2k tokens, improving cost at the price of older context availability. Overall input resembles source deltas plus bounded prior observations and periodic observation rereads for reflection, not a zero-cost background task. [Constants](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/constants.ts#L1-L66), [resource batching](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/observation-strategies/resource-scoped.ts#L227-L271), [previous-context selection](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/observational-memory.ts#L1671-L1709).

The observer prompt explicitly asks for state changes; observation groups retain attribution/range information. Reflection rewrites the current observation text and may compress away old meaning. These are useful conventions to reuse, but not proof that our failed/incomplete attempts and later corrections survive. The actor instructions also include a presumption that old plans completed; that instruction is unsuitable for fallible experience indexes and should not be imported. [Observer prompt](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/observer-agent.ts#L46-L77), [reflection prompt](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/reflector-agent.ts#L76-L90), [actor instructions](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/constants.ts#L70-L105).

The active-context threshold is **not a disk-retention bound**. LibSQL `createReflectionGeneration` inserts another generation; history and explicit clear APIs retain/access earlier generations. Its ordinary retention-table list covers threads, messages and resources, not observational memory. A latest-only derived-state policy would need explicit implementation/validation. Likewise, writing observations and their index is not one universal transaction across every backend. Abort-on-failure is the default; a continue policy can leave work pending rather than advance it, but storage/index errors still need visible handling. [LibSQL generation and clear](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/stores/libsql/src/storage/domains/memory/index.ts#L1986-L2069), [retention tables](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/stores/libsql/src/storage/domains/memory/index.ts#L106-L147), [observation persistence/index sequence](https://github.com/mastra-ai/mastra/blob/91e74210f3fee08839107f631e130afdf6d1e4bf/packages/memory/src/processors/observational-memory/observation-strategies/sync.ts#L261-L275).

## Acceptance before replacing the current policy

The LangMem spike proves an integration is technically feasible. Adoption is worthwhile when every authorized part of a long task should have an opportunity to influence the index and the user accepts more cumulative input than a fixed head/tail sample. Its 50 installed distributions and measured process footprint are real maintenance/runtime costs. They must be weighed against removing the custom incremental algorithm, not dismissed or described as free.

Use synthetic or explicitly public tasks to compare current head/tail, full small-task input and complete incremental batches on middle-only facts, later corrections, failed/incomplete outcomes, attribution and retrieval usefulness. Record actual model input/cached/output tokens, calls including failed/unknown attempts, latency and a consistent model/prompt/policy revision. Check restart recovery, oversized-message handling, output-schema failures and concurrent body updates independently. No such real-Luna quality/cost or native-hook acceptance was completed in this research. Mastra's published LongMemEval research uses its own data, models and retrieval task; those scores cannot certify this reference-index use case. [Official Mastra research](https://mastra.ai/research/observational-memory).

## Recommended macro design

This is a design recommendation, not implemented behavior. ReMe's exact reusable modules are covered by the parallel framework review; this section specifies its role rather than claiming additional ReMe source validation.

1. **Capture continuously; share an experience package.** A package represents an authorized task and contains a manifest, ordered Markdown body blocks and advisory retrieval metadata. Blocks follow complete message/structural boundaries and a size budget. Use stable public package/block IDs, sequence and hashes of canonical redacted content. Preserve full redacted text, including failed, incorrect and incomplete attempts. Carry redaction state across capture/block boundaries before making blocks publishable.
2. **Index all new content once in normal operation.** Accumulate complete bounded batches of new blocks. Call the local small model with that batch and a small previous running index, using LangMem for the state update. A single structured result contains metadata for the new blocks and the updated task navigation index. Store block metadata so facts omitted from the bounded top-level index remain discoverable through their original block and full-text search. The index remains fallible; the referenced body establishes what was actually said.
3. **Finish without a full-text merge.** At task end, flush only the final unindexed batch and update the manifest's status. Do not reread or regenerate the complete body. Later corrections append source material and explicit links to the earlier blocks; they do not erase the history. Normal cumulative model input is N+k(R+P), not repeated whole-history input. A content-unchanged sync requires no model call.
4. **Publish indexes with the body.** The contributor produces the local small-model index and publishes it as part of the package. Consumers reuse those advisory indexes and rebuild only their local retrieval structures by default; pulling another user's package does not trigger another full summarization. Exact public revision/content hashes handle mechanical deduplication. Similar experiences from different users remain distinct references with links; semantic similarity is not grounds to merge bodies or certify a winner.
5. **Give each component one role.** GitHub holds the authoritative published package revisions. Local SQLite holds capture cursors, attempts, publication state and derived indexes; unpublished local packages have a distinct pending state. ReMe provides Markdown-file retrieval behind the existing query entry point, replacing that retrieval implementation rather than becoming another fact-authoring store. Grok processes changed revisions to maintain directories, tags, links and discoverability. It does not routinely rewrite reference bodies, certify their correctness or repeat each contributor's summarization.
6. **Choose the architecture now; measure quality parameters later.** Complete-body retention, package-level sharing, complete incremental batches, a single small-model generation for local/block and task-level indexes, no final merge, and rebuildable retrieval indexes are architectural choices. Batch size, prior-index size, flush cadence, retrieval settings, correction retention and actual cost need evaluation, but their unknown numerical values do not require postponing this architecture.
