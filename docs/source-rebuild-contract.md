# 源码开发、原生重编译与产物恢复契约

[English](source-rebuild-contract.en.md) · [返回文档中心](README.md)

本契约适用于 vLLM、vLLM-Ascend 或其他框架的源码开发与重编译。用户可以从任意本地目录、没有项目目录的会话，或框架源码目录发起任务；执行策略不能依赖用户位于 MindIE Agent 仓库或读取其 `AGENTS.md`。用户明确选择的源码目录与运行环境优先；未作选择时，默认沿用目标环境中正在使用的检出和兼容运行环境。源码位置、构建输出、Python 环境与旧产物保存位置分别决定，不能因为需要重编译就自动迁移源码或创建虚拟环境。

## 统一实施顺序

以完成用户任务为准，沿现有任务记录与执行链实施，不新增通用工作区管理器、环境注册中心或平行状态机。

| 环节 | 属主与实现位置 | 完成条件 |
|---|---|---|
| 明确目标 | Agent 根据用户意图选择端点 / 容器、源码目录、解释器和是否隔离；共享工具说明直接呈现这些选择 | 新旧源码、Python 环境和清理范围分别明确；已有授权足够时直接执行 |
| 取得所需事实 | remote-dev 共享解释器与源码元数据探测；支持显式 Python 和有限候选发现 | 保留 prefix / ABI、依赖与源码路径，失败也返回已观测事实；探测不能冒充实际运行验证 |
| 选择执行方式 | 指定远端目录通过直接编辑 / shell 和资源租约运行；coordinator `run` 用于受管物化与隔离执行 | 不因编译而悄悄改变目录或执行方式；准备、运行和恢复沿用同一解释器身份 |
| 构建与恢复 | 按所选源码版本执行构建；覆盖前保存受影响基线，运行后确认加载和正确性 | Python 修改复用兼容产物，原生变化构建必要范围；失败与恢复状态分别报告 |
| 工具不适用时继续 | Agent 使用现有 CLI、宿主工具、原生 SSH 或任务临时脚本；失败响应通过 `next` 给出已知上下文与继续入口 | 标准流程不成为任务的强制门禁；保留原作业 / 端点事实，未知外部写先对账 |
| 验收与交付 | 受影响本地行为测试、无损远端检查、实际任务 Canary；先发布共享依赖，再发布消费者 | 发布前按各仓 R1–R6 验收；未执行的原生构建 / NPU 验证明确保留为待验收，不能由元数据测试代替 |

工具负责封闭的机械动作和真实结果，Agent 负责根据任务判断下一步。自动发现、标准构建、缓存复用、自动准备或收集上下文都是可替换的便利能力；必要事实可以由已授权的等价命令或脚本取得，不要求先修好 MindIE 的所有辅助能力。

## 1. 问题边界与目录选择

一次用户反馈显示：原源码位于 `/vllm-workspace/vllm-ascend`，修改并重编译后，`pip show` 的 `Editable project location` 指向了新建的 `/opt/vllm-ascend-...`。这能确认安装绑定偏离原目录；仅凭截图无法确认是哪条指令触发、原目录是否有修改、运行进程是否已加载新产物，或是否仍有可恢复的旧二进制。

对共享工具源码的检查未发现 remote-dev 自动 clone 到 `/opt` 或执行 editable 安装的逻辑。确认的缺口在于：工具 `root` 默认为 `/`，它表示文件操作边界；原 probe 只检查这个边界的 Git 信息，且不提供业务解释器选择或无导入的 editable 源码定位。这不能直接解释当时哪次调用创建了新目录，但会让 Agent 缺少沿用原环境所需的事实。其他工作区或知识库的隔离目录建议也只有在适用条件满足时才可采用。

| 情形 | 源码与运行环境处理 |
|---|---|
| 接着修改用户已有源码 | 原地修改该检出；保留用户分支、未提交修改及现有解释器绑定 |
| 明确指定新目录，并以后使用它 | 以新目录为目标，不自动搬回旧目录；按任务已有授权安装并验证新源码，旧目录是否删除另按清理授权处理 |
| 新目录复用现有 Python | 验证该解释器依赖与 ABI，按已授权意图更新目标绑定；确认共享环境占用，保留受影响旧产物与必要安装信息 |
| 明确要求两个版本同时可用 | 源码和可变安装绑定分别隔离；先验证新环境依赖，不能假设新 venv 已拥有旧 venv 的包 |
| 只读诊断或查看 PR | 优先读取现有源码或 Git 对象；无需为了阅读而切换安装 |
| 任务已在独立 worktree 中进行 | 直接复用当前 worktree；不再套一层隔离目录 |
| 明确要求并行候选、独立 PR 或版本对照 | 使用任务 worktree 和独立虚拟环境或容器；共享解释器不随之重新绑定 |
| 现有目录被其他任务写入，或与目标版本不符 | 先核实所有者、目标版本和已授权范围；解决冲突或采用独立环境，不覆盖他人改动 |

已有授权足以确定路径时直接继续。只有目录选择或共享环境切换确有歧义、且无法从现场事实和会话中确定时，才澄清受影响的动作。

“使用新目录”本身是受支持的目标，不属于目录漂移故障；“不用旧目录”不自动授权删除旧目录或终止其他任务。任务记录保留端点 / 容器、所选源码及版本、业务解释器及其 prefix / ABI、启动环境和构建输出即可，沿用现有记录，不新增一套环境状态库。

## 2. 修改前确认源码和加载关系

共享 MCP 工具的 `root` / `cwd` 字段说明及修改类工具描述必须直接披露以上边界，无需依赖知识会话或项目指令。`remote_probe(distributions=["vllm", "vllm-ascend"], python_executable="<目标环境的绝对 Python 路径>")` 读取该解释器的分发元数据、版本、安装目录与 `direct_url.json` 源码路径，不导入框架，也不创建源码目录。省略解释器时使用端点 runtime profile 后的 `python3`；输出声明隔离解释器身份，不能把它冒充为业务启动时的实际加载结果。缺少包、缺少 editable 元数据、损坏元数据分别报告，不猜测 `/opt` 或固定工作区位置。

### 多解释器的发现与选择

传入 `required_distributions=["torch", "torch-npu"]` 可启用业务解释器发现，并用 `python_candidates` 补充非常规绝对路径。工具在同一端点 / 容器 / 启动 profile 内，有限检查已绑定 `MINDIE_PYTHON`、活动 venv / Conda、PATH 和镜像常规路径，最多检查 16 个候选，共享一个总预算；未探测完的候选明确返回。控制面用于启动探针的 Python 不需要拥有 Torch，也不自动成为业务 Python。

1. 显式指定的解释器只验证该解释器，失败时不静默换用其他环境。
2. 未指定时，选择满足所需分发元数据的已绑定活动环境；没有绑定且只有一个满足时使用它。多个满足时返回 `ambiguous` 及版本、prefix、ABI、依赖与源码路径，由 Agent 按真实启动配置和源码要求决定，不按 Python 版本最高排序。
3. 保留不同 venv 的 `sys.prefix` 身份。两个 `bin/python` 可能指向同一个底层可执行文件，不能仅按 executable realpath 合并。
4. 分发元数据存在仅表示候选具备包信息。还需对照目标源码的版本 / ABI 条件；原生导入、动态库兼容及 NPU 可运行性在后续对应验证中确认，上卡仍使用租约。
5. 无候选满足时，报告每个候选缺少什么。先考虑复用已验证环境；确需隔离时在目标环境补齐匹配依赖并验证，不能向错误的 Python 临时装包以掩盖选择错误。

### coordinator 的边界

coordinator 的 `mindie.run` 把本地源代码固定为快照，并物化独立远端执行目录，可能准备任务解释器。它适用于受管隔离运行；`sources` 不表示“直接在这个远端目录修改”。用户要求在指定的现有或新远端目录开发时，使用该目录的 remote-dev 操作及 coordinator 资源租约；不能因为要编译就无意切换到物化流程。

容器就绪探测与 remote-dev 共用上述解释器发现实现，按所需 Torch / Torch-NPU（MindIE-SD 场景还包括对应框架）元数据选择，不再先选最高版本 Python。创建任务 venv 时复用已选择的 donor 解释器作为创建者，目标 prefix 和安装位置仍必须属于任务。`--system-site-packages` 不会继承另一个 venv 私有安装的包；若目标环境缺失必要包，在原生构建前明确报错，给出复用已准备运行环境或补齐匹配依赖的路径，不修改 donor 或偷偷更换系统 Python。

在实际运行的同一主机、容器、解释器与启动环境中确认以下事实，复用任务已有日志，不另建状态机或要求固定回执文件：

- 源码：Git 顶层目录的 realpath、当前 HEAD / 分支、已有 dirty diff；用户指定路径优先，不能把示例 `/vllm-workspace` 当作所有镜像的固定路径。
- Python：实际 `sys.executable`、该解释器的 `python -m pip show` / `direct_url.json` editable 目标，以及模块解析路径。必要时在正常启动环境中检查 `__file__`；避免仅通过导入框架就初始化 NPU。
- 原生产物：任务实际使用的扩展 `.so`、依赖库、自定义算子包及相关 OPP / 动态库搜索路径。`pip show` 只说明分发元数据，不能证明 Python 或原生加载结果。
- 进程：是否有运行中的服务或其他构建正在使用这些目录和产物。共享环境覆盖必须协调；不能为了本任务擅停他人的服务。

源码目录、构建目录、安装元数据与运行时解析可能各不相同。只有一致性已经确认，才能决定哪些地方需要变更；不要用额外 `PYTHONPATH` 或全局软链接掩盖冲突。

### 工具不适用时的逃生通道

Agent 发现工具缺陷、自动探测漏掉非常规环境、标准构建不支持当前检出，或 coordinator 准备流程不符合用户目标时，可以自行编写和执行当前任务所需的探测、补丁、构建、验证与恢复脚本，也可以直接使用已有 CLI 或原生 SSH。沿用会话已有授权；不要求额外启用 Skill、安装插件、创建新工作区或先将临时脚本产品化。

- **失败范围局部化**：自动解释器发现失败只说明该次发现没有完成选择。返回候选事实、未探测路径和端点参数后，Agent 可以用显式解释器或自己的脚本继续，不能把它变成所有 shell 操作的前置条件。
- **原始结果与继续信息同时保留**：失败保持 failed / blocked，`next` 提供可用的继续入口，不自动安装依赖、迁移源码、重新提交或假装已成功。coordinator 保留 execution / job 引用及资源释放事实；已存在绑定时可读取实际 target、启动环境与解释器。
- **执行与恢复保持可解释**：临时脚本使用选定端点、源码和业务解释器，正常记录命令、输出、退出码与必要恢复信息；不复制权重、另建影子记账或清理不属于本任务的进程与文件。脚本产生的新事实可替换失效的自动推断。
- **更换工具不改变外部事实**：上卡仍使用真实租约或已有已验证占用授权。已有作业可能运行、资源未释放、或外部写结果不确定时，先观察或对账；不通过另一工具重复启动、跳过归属检查或覆盖活跃产物。只暂停受影响动作，独立工作继续。
- **复用不等于强制收编**：单次脚本只需完成任务；反复出现且边界稳定的动作，之后再按证据提炼为共享工具。禁止为了符合标准工具的限制而改变用户目标。

具体入口：直接远端任务通过 `remote_bash` 执行自定义命令或上传后的脚本；受管隔离任务可向 `mindie.run` 提交本地 `script_file`，仍遵守其物化语义。remote-dev 本身不可用时，复用已授权的宿主 shell / SSH 与已知认证引用。辅助记录失败不能覆盖已确认的主操作结果。

## 3. 按变更选择最小构建范围

| 变更 | 处理方式 |
|---|---|
| 仅 Python，且当前绑定正确 | 复用原生产物；按受影响范围测试，已加载旧模块的任务自有进程需要重新启动 |
| C++ / AscendC / 头文件 / CMake / 算子注册或 ABI 改动 | 先保护受影响旧产物，再按当前检出版本支持的方式增量构建；依赖变化要求扩大时才全量重编 |
| 解释器、Torch、CANN、编译选项或目标 SoC 变化 | 旧缓存兼容性需要重新确认；禁止把其他 ABI / SoC 的产物直接当作已验证基线 |

构建命令从所选检出的构建文档和脚本获得，不能假设所有版本都支持 `build_ext --inplace`、相同环境变量或某组 pip 参数。若构建支持独立输出目录，可以把临时构建放到任务目录，源码仍来自用户选定目录。CMake 缓存中的绝对源路径必须与当前源码一致。

确需 editable 安装时，使用所选业务解释器对用户选定源码执行该版本支持的安装流程，保留依赖范围。用户明确选择新目录时，绑定到新目录；未作选择时不因重编译而新 clone 到 `/opt`。编译、安装、测试和业务启动使用一致的解释器与环境身份，避免裸 `pip` 指向另一个 Python。长编译复用已有远端后台作业管理、预算和并发槽位。

## 4. 覆盖前保留可恢复的基线

在第一次会覆盖旧产物的动作之前，识别并保存该构建 / 安装流程会替换的最小完整文件集：扩展与关联库、自定义算子包及生成注册文件、必要的安装元数据和启动环境。独立 build staging 只能避免部分覆盖，不能假设 `pip install -e` 不会同时写源码树或 site-packages。

备份放到任务结果目录或已有数据挂载，保留文件清单、原路径、是否原先不存在、校验和、软链接目标与对应版本 / 构建条件。备份必须持有真实旧字节，只有指向即将被覆盖文件的软链接不算备份。不要复制权重、整个环境或无关大目录；大文件流式处理，并核实容量。

默认保留本次修改前最后一个已验证基线，后续试验不覆盖它；用户要求多版本时再保留更多。沿用正常任务记录即可，无需新建通用产物仓库、签名或固定格式的审计回执。

源码 patch / commit、构建缓存和旧二进制分别保存。Git 不能恢复未跟踪 `.so`；一次新的 wheel 构建也不能证明重建了修改前的 editable 产物。原环境若已经不可用，备份只能标注为“修改前产物”，不能标注为“已验证可用基线”。

## 5. 验证、切换和恢复

1. 构建完成后，用与实际启动相同的解释器和环境启动新进程，核对 Python 路径及扩展 / 算子库来源。必要时用进程映射检查实际加载文件；更换磁盘文件不会更新已运行进程里的动态库。
2. 执行受影响的最小 import / 注册 / 单算子正确性检查。需要 NPU 的检查按现有租约规则执行；构建成功不能代替运行或精度验证。
3. 明确报告源码位置、修改文件、加载位置、备份位置、验证范围以及恢复方法。只有验证实际执行并通过，才能称为“已生效”。
4. 验证失败或用户要求切回时，先停止本任务使用候选产物的进程，恢复匹配的一组源码修改、产物、安装绑定和环境；保留用户其他修改。仅删除本次新增且已识别的文件，不能对共享目录执行通配清理。
5. 恢复后重新启动并重复同一范围检查。分别报告构建、安装、候选验证和恢复状态；恢复失败必须明确，不能因旧文件复制成功就宣称服务已恢复。

### 已发生非预期目录漂移时

先核对用户最终想使用哪个目录，再读取两边的 HEAD、dirty diff、安装元数据与实际启动路径，把所需修改整理为可审查 patch，保留用户已有改动。在选定目录完成必要构建与绑定验证；用户已经明确使用新目录时，不搬回旧目录。确认无活跃作业、唯一补丁或独有产物依赖待清理目录后，再按用户授权处理它。

缺少事前备份时，不能承诺原产物可一键恢复。只能查找确实存在的旧文件 / 镜像或在匹配条件下重建，并如实验证；不能仅把 editable 路径改回去就宣布修复完成。

## 6. 归属与验收边界

- **主仓**维护产品契约；**remote-dev 的实际 MCP 工具目录**承载路径、安装绑定和覆盖前备份约束，并提供源码元数据探测。宿主插件通过共享 `list_tools()` 获取相同能力，无需用户进入某个仓库或手动加载 Skill。
- **remote-dev**负责通用文件 / 命令执行、后台作业和共享解释器元数据探测；**coordinator**负责资源租约、托管执行物化及其环境准备，并复用探测实现。目录选择与构建策略由 Agent 结合任务判断，不在通用 shell 中用正则猜测 pip 或 Git 命令意图。
- **知识库**记录有适用条件和证据范围的经验；共享集群规程不自动成为每个单任务的强制 worktree 要求。

后续行为验收应观察真实文件、安装和加载结果，覆盖以下场景；此表是验收要求，不是已通过测试的声明：

| 场景 | 应观察的结果 |
|---|---|
| 任意本地目录或无项目目录发起远端任务 | 同一端点和业务解释器返回相同源码事实；工具说明始终可见，不依赖本地 AGENTS.md |
| 原目录 dirty，仅修改 Python | 修改在原检出，用户 diff 保留；绑定不漂移，没有触发原生重编译 |
| 用户明确使用新目录、停止使用旧目录 | 修改、构建和运行使用新目录，复用或隔离 Python 按意图决定，不自动搬回或删除旧目录 |
| 多个 Python，只有一个有必需依赖 | 选择满足依赖的环境；控制 Python 不被误当成业务环境 |
| 多个环境满足依赖或指定 Python 缺包 | 返回候选歧义或显式失败，不按最高版本选择或静默替换 |
| donor 的依赖仅装在其 venv 内 | 任务新 venv 缺包被提前发现，不冒充继承成功或修改 donor |
| 自动探测失败，Agent 改用任务脚本 | 原失败可见，已知端点和候选事实保留；独立脚本实际完成目标，后续 shell 未被锁死 |
| 回执不确定或资源未释放时换执行方式 | 返回原执行查询入口，保留不确定性及租约事实，不盲目重提同一操作 |
| 修改原生算子后构建成功 | 原源码位置保留，覆盖前备份存在，新进程加载候选产物并通过最小正确性检查 |
| 编译或验证失败 | 原有基线未丢失；恢复匹配文件及环境后实际检查通过，或明确报告恢复失败 |
| 明确要求并行 worktree | 候选源码与运行环境独立，共享解释器 editable 绑定未被重装 |
| pip 元数据、PYTHONPATH 或旧进程造成遮蔽 | 通过真实解析 / 加载结果发现不一致，不能只凭 `pip show` 或 build exit 0 判成功 |
