# 源码开发、原生重编译与产物恢复契约

[English](source-rebuild-contract.en.md) · [返回文档中心](README.md)

本契约规范 `vLLM`、`vLLM-Ascend` 及其他昇腾推理框架的远端源码开发、C++/AscendC 原生重编译与基线产物恢复行为。用户可以从任意本地目录、无项目目录的空白会话，或框架源码检出目录直接发起任务；执行策略不得假设用户当前位于 `mindie-agent` 仓库内或已读取其 `AGENTS.md`。

核心原则：**用户显式指定的源码目录与运行环境始终优先；用户未指定时，默认原地沿用目标环境中正在使用的源码检出与兼容 Python 环境。** 源码路径、构建输出目录、Python 解释器环境与旧产物备份路径彼此独立决策——绝不能仅仅因为需要重编译，就擅自将源码迁移到 `/opt` 或自动新建虚拟环境。

## 统一实施顺序

围绕完成用户真实目标推进，直接复用现有的任务日志与执行链路，不额外引入通用工作区管理器、全局环境注册中心或平行状态机：

| 环节 | 属主与实现位置 | 完成条件 |
|---|---|---|
| **明确目标** | Agent 根据用户意图确定目标端点/容器、源码目录、Python 解释器及是否需要隔离；共享 MCP 工具描述直接向模型披露上述边界 | 新旧源码路径、Python 环境与清理范围各自明确；现有会话授权充足时直接推进 |
| **取得所需事实** | `remote-dev` 提供免导入的共享解释器与源码元数据探测（`remote_probe`），支持显式指定 Python 或在有界预算内发现候选环境 | 完整返回 `sys.prefix`、ABI、已装依赖与源码路径，探测失败亦保留已观测到的局部事实；静态元数据探测不替代真实运行验证 |
| **选择执行方式** | 面向指定远端目录的开发通过 `remote-dev` 原地编辑/Shell 配合 `coordinator` 资源租约执行；`coordinator` 的受管 `mindie.run` 仅用于快照物化与隔离运行 | 不因触发编译而悄悄切换目标目录或执行模式；环境准备、命令运行与回滚恢复全程沿用同一解释器身份 |
| **构建与恢复** | 按目标源码检出自身支持的构建方式执行编译；覆盖前备份受影响的最小基线文件集，构建后在新进程中核验实际加载路径与算子正确性 | 纯 Python 改动直接复用兼容原生产物，C++/AscendC 改动按最小必要范围增量构建；候选验证结果与回滚恢复状态分开如实报告 |
| **工具不适用时继续** | 当标准探测或辅助流程不适用时，Agent 在已有授权内改用现有 CLI、宿主原生工具/SSH 或任务级临时脚本继续推进；失败响应通过 `next` 返回已知上下文与继续入口 | 标准辅助流程不成为阻断全任务的硬门禁；完整保留原作业与端点事实，状态为 `unknown` 的外部写入先只读对账再操作 |
| **验收与交付** | 依次完成受影响范围的本地契约测试、无损远端检查与真实任务 Canary 验证；按拓扑顺序先发底层共享组件、再发上层消费端 | 发版前按实际发布范围通过 `R1–R6` 门禁；尚未执行的原生编译或 NPU 真机验证必须如实标注为待验收，严禁用静态元数据单测冒充 |

工具负责边界封闭的确定性操作与真实状态采集，Agent 负责结合任务上下文决定下一步动作。自动环境发现、标准构建封装、缓存复用与自动准备均为可替换的提效手段——只要在用户已授权范围内，Agent 随时可通过等价命令或临时脚本获取所需事实，无需停下来等待所有辅助工具先完成改造。

## 1. 问题边界与目录选择

此前一次用户反馈显示：原始源码位于 `/vllm-workspace/vllm-ascend`，但在执行代码修改与重编译后，`pip show` 输出的 `Editable project location` 却指向了新建的 `/opt/vllm-ascend-...`。这一现象足以确认安装绑定发生了非预期的目录漂移；但仅凭单张终端截图，尚无法断定具体是哪条指令创建了新目录、原目录是否保留了未提交改动、线上运行进程实际加载了哪份动态库，以及磁盘上是否仍存有可恢复的旧版二进制产物。

排查 `remote-dev` 共享源码后确认，工具内部并不存在自动 `git clone` 到 `/opt` 或自动改写 editable 安装路径的隐藏逻辑。真实根因在于工具元信息缺口：`remote-dev` 的文件操作边界 `root` 默认为 `/`，早期 `remote_probe` 仅读取该根目录的 Git 状态，既不支持指定业务 Python 解释器，也无法在不导入重型框架的前提下解析 `direct_url.json` 中的 editable 源码真实路径。这导致 Agent 在缺乏原环境绑定事实的情况下容易误建目录；同时，工作区或知识库中关于“隔离目录/Worktree”的建议也仅在其声明的并发/多版本前提成立时才适用，不能无条件套用到单次原地开发任务。

| 场景 | 源码目录与运行环境处理准则 |
|---|---|
| **在用户已有源码上继续开发** | 直接在该检出目录原地修改；完整保留用户当前分支、未提交的 `git diff` 以及现有 Python 解释器的 editable 绑定 |
| **用户明确指定新目录并切换过去** | 以新目录为唯一开发与构建目标，不把改动自动搬回旧目录；在已有授权内完成安装绑定与验证，旧目录是否清理须单独获得明确授权 |
| **新源码目录复用现有 Python 环境** | 先校验该解释器的依赖版本与 ABI 兼容性，再按已授权意图更新 editable 绑定；排查是否有共享进程正在占用该环境，并在覆盖前备份受影响的基线产物与安装元数据 |
| **明确要求新旧两个版本并存可用** | 将源码目录与可变安装绑定彻底隔离；在新环境中独立核验完整依赖链，严禁想当然地假设新建 `venv` 会自动继承旧 `venv` 私有安装的包 |
| **只读排障或审阅 PR 代码** | 直接读取现有源码树或 Git 对象，严禁为了阅读代码而改动环境安装绑定 |
| **任务已在独立 Git Worktree 中运行** | 直接复用当前 Worktree，不再套娃创建第二层隔离目录 |
| **明确要求多方案并行候选、独立 PR 或 A/B 版本对照** | 使用任务级 Git Worktree 搭配独立虚拟环境或独立容器，保持原共享解释器的 editable 绑定不被篡改 |
| **目标目录正被其他任务写入，或分支版本与目标不符** | 先核实目录归属、目标基线版本与授权范围，协商解决冲突或改用独立隔离环境，严禁直接覆盖他人未提交改动 |

当现有会话授权与现场观测事实足以确定唯一路径时，直接执行无需反复追问；仅当目录选择或共享环境切换确实存在歧义、且无法从现场事实与对话上下文消解时，才针对受影响的动作向用户做最小澄清。

“切换到新目录开发”本身是受支持的合法目标，不属于目录漂移故障；但“不再使用旧目录”并不自动等价于授权删除旧目录或终止其上的运行进程。任务日志只需如实记录目标端点/容器、所选源码路径与 Git 版本、业务 Python 解释器及其 `sys.prefix`/ABI、启动环境变量与构建产物路径即可，直接复用现有记录结构，不另建独立环境状态库。

## 2. 修改前确认源码和加载关系

共享 MCP 工具的 `root` / `cwd` 参数说明及写操作工具描述直接写明上述目录边界，不依赖会话先加载知识库或读取本地项目规则。调用 `remote_probe(distributions=["vllm", "vllm-ascend"], python_executable="<目标环境的绝对 Python 路径>")` 可在不导入重型推理框架、不初始化 NPU、也不创建任何目录的前提下，直接读取目标解释器的包版本、安装路径及 `direct_url.json` 中的 editable 源码目录。若省略 `python_executable`，则解析端点 `runtime_profile` 生效后的默认 `python3`；返回结果显式标注该隔离解释器身份，不得将其直接等同于线上服务进程实际加载的模块路径。包缺失、无 editable 元数据与元数据损坏三类情形分别明确报告，绝不猜测 `/opt` 或硬编码工作区路径。

### 多解释器的发现与选择

传入 `required_distributions=["torch", "torch-npu"]` 可开启业务解释器自动发现，并可通过 `python_candidates` 补充非标准绝对路径。探测逻辑在同一端点、容器与启动 Profile 内，按确定性顺序扫描已绑定的 `MINDIE_PYTHON`、活跃 `venv`/Conda 环境、`PATH` 及容器镜像常见路径（最多检查 `16` 个候选解释器，共享单次总超时预算；超出预算未探测的候选路径在返回结果中显式列出）。用于拉起控制面探针的宿主机/基础 Python 无需安装 `torch`，也不会被自动当成业务运行环境。

1. **显式指定不静默回退**：调用方显式传入 `python_executable` 时，仅校验该解释器；若校验失败直接报错，绝不静默切换到其他 Python 环境。
2. **多候选歧义显式暴露**：未指定解释器时，优先采用满足依赖要求的已绑定活跃环境；无活跃绑定但全局仅有一个候选满足依赖时自动选用该环境。若存在多个候选环境同时满足依赖，则返回 `ambiguous` 状态并附带各候选的版本、`sys.prefix`、ABI、依赖与源码路径，由 Agent 结合真实启动脚本与源码要求裁定，**严禁按“Python 版本号最高”武断拍板**。
3. **保留虚拟环境 `sys.prefix` 身份**：不同 `venv` 下的 `bin/python` 软链接可能指向同一个底层系统二进制，必须按各自独立的 `sys.prefix` 区分环境身份，不得仅凭可执行文件 `realpath` 合并去重。
4. **静态元数据与运行时验证分层**：`dist-info` 元数据存在仅证明包已安装，不证明 C++ 扩展可正常 `import`、动态库 ABI 兼容或 NPU 设备可用；后续仍须在对应阶段结合真实 NPU 租约完成导入与算子验证。
5. **缺包诊断与精准补齐**：无任何候选满足要求时，逐一列出各候选缺失的分发包。优先复用已准备好的兼容环境；确需新建隔离环境时，在目标隔离环境中补齐匹配依赖并验证，严禁往误选的 Python 环境中临时 `pip install` 来掩盖环境选择错误。

### coordinator 的边界

`coordinator` 的受管任务绑定（`context_file`）并非测试 SSH 连通性、盘点主机/NPU/容器、定位源码与权重路径或运行纯 CPU 测试的前置条件。`hosts`、`probe`、`container` 与 `lease` 均为独立环境接口，省略 `context_file` 即可直接调用（涉及物理设备占用时仍由宿主租约队列统一仲裁）。在未建立受管任务关联时，Agent 可正常执行上述探测与已授权的直接排查；仅当具体物理卡、目录或进程的归属确实无法确认时，才暂停依赖该资源的步骤。

`coordinator` 的 `mindie.run` 会将本地源码打包为只读快照，在远端物化出独立的执行目录并按需准备任务级解释器——它专为**受管隔离运行**设计，其 `sources` 参数代表本地输入快照，而非“直接在某个远端目录原地改代码”。当用户要求在指定的远端现有目录或新目录中开发时，应直接组合使用 `remote-dev` 文件/命令操作与 `coordinator` 设备租约，切勿仅仅因为需要编译就无意切入 `mindie.run` 快照物化流程。

容器就绪探测与 `remote-dev` 共用同一套多解释器发现逻辑，统一按 `torch` / `torch-npu`（在 `MindIE-SD` 场景下连同对应扩散框架包）分发元数据筛选业务环境，不再盲选最高版本 Python。基于 Donor 解释器创建任务级 `venv` 时，目标 `sys.prefix` 与包安装路径归当前任务独占；由于 `--system-site-packages` 无法继承另一私有 `venv` 内部安装的依赖，一旦检测到目标环境缺失必需依赖，系统会在启动耗时原生编译前提前报错，并提示复用现有兼容环境或显式补齐依赖，绝不污染 Donor 环境或悄悄回退到系统裸 Python。

动手修改代码前，应在真实运行的目标主机、容器、业务解释器与启动环境中核清以下四项事实（直接记录在现有任务日志中，无需新建状态库或强制生成固定格式回执）：

- **源码树**：Git 仓库顶层目录的 `realpath`、当前 `HEAD` 提交与分支、以及已有的未提交 `git diff`。始终以用户指定路径为准，切勿把示例文档中的 `/vllm-workspace` 当作所有容器镜像的固定目录。
- **Python 绑定**：实际 `sys.executable`、该解释器下 `python -m pip show` 与 `direct_url.json` 指向的 editable 源码路径，以及模块搜索路径；必要时在真实启动环境变量下核对模块 `__file__`（注意避免仅为查路径而触发 `torch_npu` 设备初始化）。
- **原生二进制产物**：当前实际加载的 C++/AscendC 扩展 `.so`、关联动态库、自定义算子包以及 `ASCEND_CUSTOM_OPP_PATH` / `LD_LIBRARY_PATH` 搜索链。`pip show` 只能反映静态安装元数据，不能证明进程实际加载了哪份 `.so`。
- **活跃进程占用**：检查是否有线上推理服务或其他编译任务正在读写同一批目录与二进制文件。共享环境变更必须先协调确认，严禁为了跑当前任务擅自杀掉他人的服务进程。

源码目录、构建缓存目录、`dist-info` 元数据与运行时实际解析到的文件路径可能彼此不一致；必须先查明差异根源再动手修改绑定，严禁靠临时塞入 `PYTHONPATH` 或打全局软链接掩盖路径冲突。

### 工具不适用时的逃生通道

当遇到辅助工具自身缺陷、自动探测漏掉非标环境、标准构建脚本不支持当前源码分支，或 `coordinator` 默认准备流程偏离用户意图时，Agent 完全可以在当前会话已有授权内，直接编写并执行针对当前任务的探测、打补丁、编译、验证与恢复脚本，或直接调用现有 CLI 与原生 SSH——无需额外激活 Skill、安装新插件、新建工作区，更无需先把一次性脚本封装成通用产品工具。

- **故障影响面局部化**：自动解释器发现失败仅代表“本次自动筛选未能替你拿主意”。工具返回已采集的候选事实、未探测路径与端点参数后，Agent 即可显式传入 `python_executable` 或改跑自定义脚本继续推进，绝不让自动探测失败锁死后续所有 Shell 操作。
- **真实报错与继续路径并存**：失败操作如实保持 `failed` / `blocked` 状态，同时在 `next` 字段中给出可执行的继续入口，绝不自作主张偷装依赖、搬移源码、自动重提作业或伪装成功。`coordinator` 完整保留 `execution` / `job` 引用与资源释放记录；已有绑定时可直接查询真实 `target`、启动环境与解释器路径。
- **自定义脚本透明可追溯**：任务级临时脚本同样在选定的端点、源码目录与业务解释器下运行，如实记录执行命令、标准输出、退出码与回滚信息；不复制大模型权重、不建影子账本、也不误删非本任务创建的进程与文件。脚本实测得到的新事实可直接替代失效的自动推断。
- **切换工具不抹除外部事实**：只要涉及上卡运行，仍须遵守真实的 NPU 租约或已确认的独占授权。若前序作业可能仍在运行、设备尚未释放，或某次外部写入处于 `unknown` 状态，必须先观测或只读对账，严禁换个工具直接重跑覆盖活跃产物；等待对账期间仅暂停存在依赖的步骤，其余独立分析工作照常推进。
- **单次救急与沉淀抽工具解耦**：一次性脚本把当前用户任务干净闭环即可；只有跨多次任务反复出现、输入输出边界高度稳定的机械动作，后续才值得按实证提炼为共享工具。绝不能为了迁就现有工具的局限性而强迫用户改变任务目标。

常用逃生入口：直接远端开发任务可通过 `remote_bash` 执行自定义命令或上传后的任务脚本；受管隔离运行任务可通过 `mindie.run` 提交本地 `script_file`（遵循其快照物化语义）；当 `remote-dev` 服务本身不可用时，可在已有授权内直接复用宿主原生 Shell / SSH 与已知认证凭据。任何次要日志或本地回执写入异常均不得反转已确认成功的远端主操作结果。

## 3. 按变更选择最小构建范围

| 代码或环境变更类型 | 推荐构建与生效方式 |
|---|---|
| **纯 Python 代码改动（且当前 editable 绑定正确）** | 直接复用现有 C++/AscendC 原生二进制产物；按受影响模块运行测试，并重启本任务名下已加载旧版 Python 模块的进程 |
| **C++ / AscendC / 头文件 / CMake / 算子注册或 ABI 改动** | 覆盖前先备份受影响的基线二进制与注册文件，随后按当前源码检出支持的方式执行增量构建；仅当底层头文件或构建图变化要求扩大范围时才执行全量重编 |
| **Python 解释器、`torch`、CANN、编译宏或目标芯片 SoC 变更** | 重新核验已有构建缓存的二进制兼容性；严禁将其他 ABI 或其他 SoC（如混用 `910B` 与 `910_93`）编译出的产物直接当作可用基线 |

具体构建命令应直接读取目标源码检出自身的构建文档、`setup.py` / `pyproject.toml` 或构建脚本，不得想当然地假设所有分支版本都支持 `build_ext --inplace`、相同的环境变量开关或同一组 `pip` 参数。若构建系统支持独立 `build` 输出目录，可将中间编译产物放入任务级临时目录，同时保持源码读取自用户选定目录，并确保 `CMakeCache.txt` 中缓存的源码绝对路径与当前目标检出严格一致。

确需重新执行 editable 安装时，显式使用选定的业务 Python 解释器（`<python_executable> -m pip install --no-build-isolation -e <源码目录>` 等与版本匹配的命令）安装用户指定目录，避免裸敲 `pip` 误装进另一个 Python 环境。用户明确指定新目录时绑定至新目录；用户未指定时，严禁因为重编译而在 `/opt` 下另起炉灶新克隆一份仓库。耗时较长的原生编译统一走 `remote-dev` 后台长作业管理与 `coordinator` 编译并发槽位预算。

## 4. 覆盖前保留可恢复的基线

在执行任何可能改写现有二进制或安装绑定的首个动作前，先识别并备份本次构建/安装将会覆盖的**最小完整基线集合**：包括目标 `.so` 扩展与关联动态库、自定义算子 OPP 包及自动生成的算子注册文件、必要的 `dist-info`/`direct_url.json` 安装元数据以及启动环境配置。注意：即便配置了独立的中间 `build` 目录，`pip install -e` 仍可能原地覆写源码树内的 `.so` 或 `site-packages` 下的 `.pth`/元数据，不能省略备份。

备份统一存放在当前任务结果目录或既有大容量数据挂载盘下，完整记录文件清单、原始绝对路径、修改前是否原本不存在、SHA256 校验和、软链接指向目标以及对应的 Git Commit / 构建条件。**备份必须保存真实的旧文件字节内容**——仅创建一个指向待覆盖原文件的软链接起不到任何保护作用。同时严禁备份大模型权重、整套虚拟环境或无关大目录；遇到体积较大的动态库时采用流式拷贝并提前核验磁盘余量。

默认锁定保留**本次任务动手修改前的最后一个已验证可用基线**，后续多轮迭代试错不得覆盖该初始基线（仅在用户明确要求保留多代历史版本时才额外增存）。备份清单直接写入常规任务记录即可，无需额外发明一套通用产物仓库、数字签名或固定格式的审计回执协议。

源码改动（`git diff` / patch / commit）、构建中间缓存与旧二进制产物三者分开保存：单靠 `git checkout` 无法找回未被 Git 跟踪的预编译 `.so`，重新打一个新 wheel 包也不等于还原了修改前的 editable 运行态。若接手任务时原环境本身已处于损坏状态，备份文件必须如实标注为“修改前原始产物”，不得虚标为“已验证可用基线”。

## 5. 验证、切换和恢复

1. **新进程加载路径核验**：构建完成后，使用与线上真实启动完全一致的业务解释器和环境变量拉起新进程，核对 Python 模块 `__file__` 及 C++/算子动态库的真实加载路径（必要时检查 `/proc/<pid>/maps`）。注意：替换磁盘上的 `.so` 文件不会热更新已驻留内存的运行中进程。
2. **最小闭环正确性验证**：运行受影响模块的最小 `import`、算子注册表检查与单算子数值正确性测试（需要上卡的测试严格通过现有 NPU 租约执行）。编译返回 `exit 0` 绝不等于运行时加载成功或数值精度达标。
3. **透明交付关键事实**：向用户清晰汇报源码目录、修改文件清单、实际加载产物路径、基线备份路径、已完成验证范围以及一键回滚命令。唯有上述运行验证真实通过后，才可报告改动“已生效”。
4. **精准回滚与无损清理**：一旦候选产物验证失败或用户要求切回原版，先干净停止本任务拉起的候选测试进程，再成套恢复匹配的源码状态、基线二进制、editable 安装绑定与环境变量，同时妥善保留用户原有的其他未提交修改。仅删除本次构建明确新增的文件，**严禁在共享目录上执行通配符 `rm -rf` 清理**。
5. **回滚后复验**：恢复旧基线后重新拉起进程并跑通同等范围的加载与功能检查，将构建结果、安装结果、候选验证结果与回滚恢复结果分项如实汇报——绝不能仅仅因为旧文件 `cp` 成功就直接宣布服务已恢复正常。

### 已发生非预期目录漂移时

若接手现场时已发生目录漂移（如环境已被绑到 `/opt/...`），先与用户确认最终希望保留哪个目录作为唯一工作目录；随后比对新旧两处目录的 `HEAD`、`git status`/`diff`、安装元数据与线上进程实际加载路径，将有效代码改动提取为可审阅的 Patch 并妥善保留用户原有修改，在最终选定的目录上重新完成构建与加载路径核验。若用户明确决定直接沿用新目录，则不要强行把代码搬回旧目录；待确认无任何活跃作业、独有补丁或唯一二进制产物依赖废弃目录后，再在用户明确授权范围内清理旧目录。

若漂移发生前未留存二进制备份，切勿向用户承诺可一键秒级还原旧二进制——此时应如实检索磁盘或基础镜像中尚存的旧产物，或在严格匹配的源码与编译条件下重新构建并完成实机验证，绝不能只把 `.pth` / `direct_url.json` 路径改回原目录就草率宣布修复完成。

## 6. 归属与验收边界

- **主仓（`mindie-agent`）** 维护本跨仓产品契约；**`remote-dev` 的共享 MCP 工具目录**在参数 Schema 与工具描述中直接内建路径边界、安装绑定与覆盖前备份提示，并提供免导入源码与解释器元数据探测。所有宿主插件通过共享 `list_tools()` 自动继承同一套约束与能力，无需用户切入特定仓库或手动加载 Skill。
- **`remote-dev`** 负责通用远端文件读写、命令与后台长作业执行以及多解释器元数据探测；**`coordinator`** 负责物理设备/端口租约、受管隔离执行目录物化及其运行环境准备，并直接复用 `remote-dev` 的解释器探测实现。具体目录选择与最小构建策略由 Agent 结合任务上下文判断，严禁在通用 Shell 工具内部写脆弱的正则表达式去猜测用户的 `pip` 或 `git` 意图。
- **领域知识库（`knowledge-*`）** 按明确的适用条件与证据边界提供参考经验；面向多人共享集群的 Worktree 隔离规程不会自动变成单人原地开发任务的强制枷锁。

相关工程实现的行为验收必须直接核验真实磁盘文件、安装元数据与新进程动态库加载结果（下表定义后续验收判据，不代表所有条目均已在当前静态文档提交中跑完）：

| 验收场景 | 必须观测到的真实行为结果 |
|---|---|
| **从任意本地目录或无项目会话发起远端开发** | 对同一远端端点与业务解释器返回完全一致的源码与绑定事实；MCP 工具边界说明始终可见，不依赖本地存在 `AGENTS.md` |
| **原源码目录含未提交改动，且本次仅修改 Python 文件** | 代码直接改在原检出目录，用户原有 `git diff` 完好保留；editable 绑定零漂移，且未触发多余的 C++/AscendC 重编译 |
| **用户明确指定切换至新源码目录** | 代码修改、编译与运行均落在新目录，按用户意图复用或隔离 Python 环境，不自动搬回旧目录，也不擅自删除旧目录 |
| **容器内存在多个 Python，仅一个具备完整推理依赖** | 准确选中满足 `torch`/`torch-npu` 依赖的业务解释器，不会将控制面探针 Python 误判为业务环境 |
| **多个 Python 同时满足依赖，或显式指定的 Python 缺包** | 如实返回 `ambiguous` 候选列表或显式缺包错误，绝不按最高版本号盲选或静默替换解释器 |
| **Donor 解释器的依赖仅装在其私有 `venv` 内** | 新建任务级 `venv` 时在启动原生编译前即精准拦截缺包问题，既不假装继承成功，也不反向污染 Donor 环境 |
| **自动探测受阻，Agent 改用任务级脚本继续** | 原始探测失败与已知端点/候选事实清晰可见；独立脚本顺利跑通任务目标，后续常规 Shell 调用不被锁死 |
| **外部回执 `unknown` 或租约未释放时切换执行方式** | 完整保留原作业查询入口、`unknown` 状态与设备租约归属事实，先对账后操作，绝不盲目重复提交同一写入 |
| **修改 C++/AscendC 原生算子并增量编译成功** | 源码留在原位未漂移，覆盖前基线备份真实存在，新拉起的进程确认加载新 `.so` 并通过最小算子正确性校验 |
| **原生编译失败或新产物精度验证未通过** | 修改前基线完好无损；成套恢复源码、旧二进制与环境后新进程复验通过（若恢复异常则显式报错，绝不假报已恢复） |
| **用户明确要求多分支并行 Worktree 对照** | 候选分支的源码与运行环境彻底隔离，原共享解释器的 editable 绑定未被篡改 |
| **`pip` 元数据、`PYTHONPATH` 或长驻旧进程造成加载遮蔽** | 通过真实新进程模块解析与动态库路径检查揪出不一致，绝不单凭 `pip show` 路径正确或编译 `exit 0` 误判生效 |
