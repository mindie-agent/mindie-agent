# 发布兼容与静默更新

[English](release-compatibility-and-update.en.md) · [返回文档索引](README.md)

状态：2026-10-16 当前产品合同；首个普通内测 Release `0.0.1` 已发布。
本文替代此前“全部版本选择交给 Git marketplace”及“不同安装绑定一律拒绝”
的限制。实际实现、配套组件发行状态和六组合证据以
[0.0.1 发布记录](releases/0.0.1.md) 为准。

## 组件与插件配套发布

产品发布的是经过验证的组件组合。各软件仓库独立维护版本，产品 `0.0.1`
不要求 remote-dev、knowledge 或 diagnostics 也叫 `0.0.1`；已有组件版本
不得为统一显示而倒退或重编号。未变化的组件复用已发布版本，无需陪同涨号。
第三方依赖继续由完整依赖锁固定，不要求代第三方创建 Release。

按照依赖顺序发布：先 diagnostics，再发布依赖它的 remote-dev 和 knowledge，
最后发布固定这些组件的各 Harness 插件及统一产品入口。互不依赖的组件可以
并行准备、验证和发布。组件可以独立迭代，但插件只通过新的组合发行采用变化，
已发布插件不会绕过依赖锁自动追逐某个组件的 `main` 或 `latest`。

发布执行者必须在产品发布记录中填写以下清单。它是开发交付要求，不增加用户
确认、普通任务检查或新的运行时管理机制；复用各仓库现有构建和发行流程。

| 发布前核对 | 所需事实与缺项处理 |
| --- | --- |
| 完整依赖清单 | 从每个插件最终源码的依赖锁读取直接及传递的第一方软件组件；列出仓库、包名、包版本、完整提交 SHA 和对应 Release，不能只列产品入口 |
| 组件已正式发行 | 每个依赖均有非 draft、非 prerelease 的已发布 Release；仅有 tag、候选、合入或绿色 CI 不算完成 |
| 身份逐项一致 | 解引用 annotated tag 后的提交必须等于插件锁定提交；tag 版本、源码包版本和 wheel/sdist 元数据一致，不能用相同版本号掩盖不同代码 |
| 产物可获取且完整 | 从正式 Release 下载构建产物和校验文件，核对 SHA256、包内元数据及运行时代码与固定源码的对应关系；上传成功不能替代下载验证 |
| 验收范围明确 | 分别记录实际原生安装身份、组件/包检查及后续源码变化；没有重跑的测试不能归为新 tag 的实机证据，失败和 unknown 保留 |
| 组合闭环 | 组件全部完成后才发布插件；核对插件锁与组件 Release 映射，回读各 tag、Release flags、资产和统一发行记录；缺任一项即保持该项未完成 |

tag 可以指向已合入主线的精确候选提交，不要求为了使用 merge commit 改写
已验收的依赖锁。后续 merge 只改测试或文档时，保留两个提交和差异说明，
不能因为生产文件相同就谎称提交相同。若需更换实际组件代码，应重新核对组合、
补受影响验证并发行新版本；不移动旧 tag、不覆盖同名资产或已发布插件的依赖锁。
外部发布操作结果未知时先读取原对象，不盲目重试上传或创建。

`knowledge` 是经验采集、整理、检索和分享的软件组件，应有软件 Release。
`knowledge-vllm-ascend` 是知识内容仓库，按已固定的内容合同、Git 提交和块
哈希持续分发；新增正文不要求同步发布软件版本。内容合同或格式变化才需要
与运行时、Bot 和插件支持协调。内容快照不能替代运行时组件的 Release。

## 发布声明与唯一选择

每个插件的正式 Release 都声明自己的产品版本、官方来源和精确源码提交，
以及支持的 Harness 名称和版本区间。当前安装的 Harness 版本决定候选集合，
使用成熟 SemVer 解析与排序，选择其中最高的正式 Release；不自动降级，不把
draft、prerelease 或开发 main 当成普通发行。Harness 自身为 alpha 时，必须由
区间明确允许，不能因插件是正式 Release 就猜测支持全部 Harness 预览版。

区间由发布者依据接口合同和验证证据确定，不以两个端点通过推断中间全部兼容，
也不以同名选项或未知字段被宿主忽略作为支持证据。单点可用闭区间表达；
有证据后再扩大区间。每次发行使用不可变版本和提交，不覆盖同版本源码。

每个插件仓库保存机器可读的 `harness-compatibility.json` 和集中接口清单。
发布产物将该声明与最终源码 SHA 绑定，避免源码文件自引用其所在提交。
接口清单至少记录：

| 内容 | 作用 |
| --- | --- |
| 接口 ID、所属 Harness 和支持区间 | 统一声明 Hook、MCP、CLI 参数、环境变量和原生输出合同 |
| 生产调用位置 | 能定位实际用到接口的代码，禁止只有文档没有接线 |
| 官方依据或固定版本源码 | 区分公开支持、已核对实现与待验证假设 |
| 对应测试及实机证据 | 覆盖原生返回值、失败语义、平台差异及关键边界 |
| 发布实际使用的接口集合 | 发布支持范围必须落在全部必需接口支持范围内 |

发布检查校验声明、调用清单、版本、来源、固定依赖和区间覆盖关系。测试存在
不等于测试通过；无法证明支持的接口或平台保持待验，不发布虚构的宽范围。
同一共享选择函数供两端使用，不各写一套版本比较器。

原生管理器负责包下载、安装、缓存和已安装记录。若原生格式无法表达兼容
选择，适配器只把选出的固定候选交给它；本地 catalog 是选择结果的派生投影，
不能成为第二份版本决策。不得同时启用能绕过兼容筛选的无条件最新版本更新。
GitHub Release 的固定官方来源、发布声明和下载后实际提交必须相互一致。
首次安装也使用原生安装器固定到不可变 Release tag，不从移动的 `stable`
或 `main` 追新。首装核对该 Release 对实际 Harness 的支持范围；后续更新
才由上述共享选择结果驱动原生安装，避免初始安装到首次检查之间绕过兼容筛选。

## 联网执行与静默语义

距离上次成功检查超过 24 小时，在下一次自然使用时异步执行上述策略。
不询问用户、不要求确认、不发送更新通知，也不要求手动 reload。
沿用安装时保存的授权、项目范围、明确停用和独立故障上报选择。
代码更新本身不启用贡献、不扩大采集范围，不改模型或宿主的全局权限设置。

检查接入已有启动和活动维护入口；短 Stop 不承担网络、依赖安装或升级。
普通调用只做进程内轻量判断，首次进入进程至多读取小份本地检查记录；
不能每次访问网络、扫描 Release 列表或哈希完整运行时。同一时刻只有一个
后台检查/安装操作，其他入口合并到已有检查，不等待它完成。

“成功检查”指完整读取并验证官方发行信息、完成兼容选择；没有新版本也是成功。
检查失败不改成功时间，单独失败退避避免断网或限流期间每次使用都重试。
检查成功而下载失败分别记录。已经准备的版本在后续安全时机尝试切换，
不等待下一个 24 小时，也不重复下载或重新获取发行历史。
断网、无兼容候选或临时下载失败均保留可用安装；
已开始而效果未知的安装先核对，不能并发重装。
不能把仅测试“启动检查”写成已经验证了长会话断网恢复后的自动检查。

没有产品进程运行时，不为追新另造常驻更新服务。产品运行时联网检查的触发、
并发合并及请求成本需由实现和验收明确，不能用文档承诺代替接线。
例行更新状态只记录在可查询的本地诊断中，不注入模型上下文或更新提示。
实际业务接口失败仍遵循原则 9；静默更新不意味着吞掉业务错误。

## 准备、切换与恢复

采用成熟服务的准备、排空、切换和就绪检查流程，复用现有安装锁、原生安装器、
不可变运行时与精确服务所有权，不新增 supervisor、会话租约或多代后继链。

1. **后台准备。** 在活动安装之外下载固定版本、同步完整依赖锁、核对包与接口，
   生成完整的新运行时。准备失败不修改活动绑定，不能在短切换窗口下载或编译。
2. **等待空闲。** 活动 RPC、已准入采集或摘要仍忙时继续使用旧安装，并推迟
   切换。不能靠等待时长推断业务失败，也不能因有新版而重做原操作。
3. **短暂切换。** 使用既有锁阻止新操作进入，确认旧 owner 空闲，完成精确退出，
   确认新服务就绪后原子替换唯一的安装绑定。解释器、脚本与 engine 配置作为
   完整身份切换，禁止新解释器执行旧脚本或原地改写活动 engine。
4. **恢复接口。** 新调用在短窗口等待，或得到明确的暂时不可用、尚未执行结果。
   已加载的原生入口仍可使用其稳定路径，后续调用读取现用完整绑定；迟到 Hook
   和旧 SessionStart 不参与版本选择，不把安装切回去，不要求用户重新加载。
   不会自动重发的 Stop 事件需要先进入已有持久采集队列，不能只因切换锁忙就
   丢弃本次采集。持久入队与唤醒服务分开；沿用贡献范围、身份、停用及格式检查，
   不唤醒已退役 owner，不新增第二套事件队列。
5. **保留失败事实。** 切换前失败继续使用旧版；切换中断后根据原生安装记录和
   现用绑定核对恢复阶段，不猜测成功。旧 owner 已退出、新 owner 未就绪必须
   单独验证恢复路径，不以“已安装”冒充可用，也不重放未知业务。

30 秒作为切换控制阶段的候选观察窗口，最终数值以三平台实测确定。该窗口
不包含下载或依赖安装，也不限制模型、远端执行或摘要的业务寿命。窗口超出时
保留真实阶段和结果，不强杀在途业务、不盲目并发启动；若存在真实不可用，
由业务接口准确报告，后台更新本身不发通知。

借鉴成熟产品的是明确的准备和切换边界，不是复制完整发布控制器。NGINX 的
配置预检、失败保留原工作进程和旧请求排空是参考；带期限后强杀 worker 的
策略不适用于本产品结果可能未知的模型与远端操作。
参考 [NGINX 官方控制说明](https://nginx.org/en/docs/control.html)；已保存
2026-10-15 官方页面快照及 SHA256。其双 worker 策略不是本产品的实现要求，
本产品允许短暂不可用，复用现有单 owner 的空闲退出与启动即可。

## 必须通过的行为验收

先用无模型原生进程和本地发行 fixture 验证，再补受影响的六组合业务验收：

- 新版不支持当前 Harness 时，选择较低但最高兼容 Release；无候选不降级，
  Harness 版本未知、声明损坏和来源冲突不得装错版。
- 不增加授权或更新提示；原停用、范围、已保存正文、游标、usage 和 unknown
  保留，原生记录、源码 SHA、依赖锁和现用绑定分别回读。
- 后台准备期间旧接口正常；业务忙时不切换；短切换窗口的请求明确未执行，
  恢复后旧入口、新入口和迟到 Stop 均正常，不回切、不要求 reload。专门在
  切换窗口派发真实 Stop，核对事件已持久入队、切换后仅处理一次，不能用
  切换完成后再发 Stop 替代这一边界。
- 覆盖切换前失败、退休后写配置失败、进程中断、新服务启动失败和并发检查，
  记录实际不可用时长、主错误及恢复结果，不用固定 sleep 冒充就绪。
- 成功检查后 24 小时内的连续使用不访问更新网络；到期后并发自然使用合并为
  一次异步检查。失败不刷新成功时间，失败退避阻止逐次调用重试；待切换候选
  不重复下载。长会话联网恢复后能继续检查；短 Stop 不联网、不安装、不续跑模型。

产品 Release 排序、Harness 接口支持区间、数据 `FORMAT` 与服务归属是不同
事实。正式发布后的数据字段变化仍需实际兼容设计；当前不维护未发布版本的
迁移或多代协议分支。上述要求不能靠旧实验的版本标签或绿色组件测试冒充完成。
