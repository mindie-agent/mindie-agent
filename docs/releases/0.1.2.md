## 一次配置与后续连接

在终端隐藏输入一次远端 SSH 密码：

```bash
remote-dev auth setup --host 192.0.2.10 --port 22 --user root --prompt
```

配置先验证已有 OpenSSH 身份；需要公钥时，安装并独立验证所选公钥，同时保留密码供后续恢复。服务端不接受公钥、但密码认证成功时，保存密码认证方式，后续进程直接使用。明确只使用密码时可加 `--no-install-key`。`--password-env VARIABLE` 只导入一次，后续进程不需要保留该环境变量；自动化入口也可通过标准输入导入密码。

默认配置位于当前用户的 `~/.mindie/ssh`，按准确的 `host + port + user` 识别连接。秘密保存在本地明文文件 `credentials.json`，连接配置只保存引用。目录与文件使用所在平台的用户权限保护，不调用系统钥匙串或凭据保险库，不要求系统登录密码、解锁密码或新的主密码。该目录应按 SSH 私钥目录保护。

同一环境、同一操作系统用户下的进程、聊天和插件可直接共享认证。原生 Windows 与 WSL 各自使用所在环境的用户目录，不默认跨两套用户目录复制秘密。覆盖 `REMOTE_DEV_AUTH_DIR` 或 `REMOTE_DEV_CREDENTIAL_FILE` 时，各入口应使用相同配置；主机别名和 IP 不会自动合并为同一连接。

## 公钥修复、只读监控与错误边界

- 对已保存恢复密码的公钥连接，普通开发调用在提交业务前检查公钥。只有确认认证被拒绝后，才使用恢复密码验证连接、重新安装并验证同一公钥；业务命令只提交一次。
- 安装采用共享实现，保留已有 `authorized_keys` 内容，支持原文件没有末尾换行的情况。不会修改 `sshd` 配置。
- 密码可用但公钥维护失败时，保留密码连接能力，并在调用结果中返回认证维护事实。维护失败、已完成安装和不确定的远端写入分别记录；维护结果未知时中止当前调用并保留密码，不会把未确认的写入当作成功或自动重放业务。
- 只读诊断和 `npu-top` 监控可在同一次 SSH 握手内由公钥回退到密码，不修复公钥，也不改写认证配置。主机指纹冲突继续报错。
- `auth status` 查看非秘密状态；`auth forget` 删除本地连接配置和保存的密码，不撤销远端公钥或删除共享私钥。密码变更后重新执行配置命令。

原生 Windows 使用安装包生成的 `remote-dev-askpass.exe`，密码通过 UTF-8 标准输出交给 SSH；POSIX 使用同一认证模块的独立 helper。一次性验证码、交互式 MFA、密码到期后的修改流程不在保存密码登录的覆盖范围内。

| --- | --- | --- |

| Windows Server 2025，PowerShell 7.6.7，Python 3.12.10 | 4 passed，0 failed/errors/skipped；17.503 秒 | 本机 Git OpenSSH 10.5p1 连接 WSL 内真实 Linux sshd；四条核心路径全部通过 |

| WSL2 Ubuntu 24.04，Python 3.12.3 | 4 passed，0 failed/errors/skipped；17.338 秒 | WSL2 内的 Linux OpenSSH 9.6p1 连接真实 sshd；四条核心路径全部通过 |

Windows PowerShell 与 WSL2 的四条核心路径分别是：密码录入后安装公钥并由新的独立 venv 复用；服务端关闭公钥认证后跨进程保存密码；公钥撤销后先修复且业务写入恰好一次；已安装的 `coordinator`、真实 Kimi adapter 的两个聊天和两个 venv、以及重新打开数据库的 `npu-top` 共享凭据。测试还覆盖非 ASCII 密码、带空格路径、隔离进程导入与 `pip check`。WSL 证据核对了实际 WSL2 内核，未用普通 Linux 结果代替。

这些测试使用隔离认证根目录中的默认 `credentials.json` 和一次性 sshd 账户，不读取用户既有凭据。Windows 的实测客户端是产品选择的 Git OpenSSH，不能据此声称 Windows 内置 OpenSSH 的所有版本均已验收。三平台结果是 SSH 控制面的正确性验收，不是 NPU 性能测量。

CI 来源为 [真实 Windows/WSL 验收](https://github.com/mindie-agent/remote-dev/actions/runs/40777028005) 和[普通合同测试](https://github.com/mindie-agent/remote-dev/actions/runs/40777027999)。三环境共 19 项真实测试使用同一份 CI wheel 组合。实际构建的 PR merge 提交为 `f3592ffdef033aecb3d24b027dbd889204b65b28`，与 正式 `remote-dev 0.11.1` 源码 `2a750ec8c74d7f053410d48dd820aeb542e7d3b1` 的 Git 树完全相同。`coordinator` 和 `npu-top` 保留实际测量提交，并单独记录其与后续正式依赖 pin 的运行时代码等价性；不把后来的元数据提交冒充为原测试源码。文件摘要、旧基线结果和范围见[认证验收记录](https://github.com/mindie-agent/mindie-agent/blob/v0.1.2/docs/releases/0.1.2/ssh-auth-acceptance.json)。

## 插件发现与升级范围

四个宿主的远端 MCP 目录均在 `remote-dev 0.11.1` 上重新通过真实 stdio `tools/list` 检查：Codex 23、Claude Code 31、Kimi 30、DSH 23 个工具，包含 `remote_auth`，暴露 `password_env` 而不提供明文 `password` 参数。Codex 与 Claude Code 使用安装的插件 wheel；Kimi 使用原生插件源码与已安装组件；DSH 直接挂载共享 MCP。四个独立 venv 的正常依赖解析、隔离导入与 `direct_url.json` 均确认 `remote-dev` 来自 `2a750ec8c74d7f053410d48dd820aeb542e7d3b1`，诊断组件为正式 `0.5.4`。这次安装的知识基线分别为 Codex/Claude Code `0.13.4`、Kimi/DSH `0.13.3`，均如实保留在验收记录中。

正式发布后，在 macOS arm64 的独立原生配置中，从旧正式插件及其原始更新器启动普通检查，通过官方 Release 源选择并安装新版本，未使用强制更新、候选源覆盖或伪造宿主版本。具体旧版、新版、宿主版本、已安装依赖与目录检查见[原生更新验收](https://github.com/mindie-agent/mindie-agent/blob/v0.1.2/docs/releases/0.1.2/native-update-acceptance.json)。首次 Claude Code、DSH 临时目录别名失败，以及 Codex 使用不受支持的自定义本地市场夹具导致的失败，均保留在记录中；随后按各自支持的规范路径或正式来源目录重新创建旧版安装，原更新器成功完成升级。

这证明隔离旧安装的正常更新路径与更新后适配器目录，不表示用户已有安装已全部升级，也不表示常驻聊天已加载新工具定义。Kimi、DSH 的回执明确要求宿主重载；各宿主继续遵循自然重载或新进程边界。初始安装中 Kimi/DSH 的知识基线为 `0.13.3`，正常独立更新会选择正式 `0.13.4`，两阶段分别记录。

Codex 另在最终 `46a3401904b736fd7dd10a822b8d883be1252acf` 源码上完成原生 CLI `0.153.4` 冷安装验收：12 项通过，pytest 耗时 `28.93s`（完整进程 `29.654s`），覆盖原生市场安装、五个 Hook 与信任/显式禁用行为，以及新原生线程发现 23 个远端工具和 5 个组件入口；已安装 `remote-dev` 确认为 `0.11.1 / 2a750ec`。本轮未执行模型会话，不扩张为四宿主远端业务端到端验收。

Codex Windows 发布前 CI 首次因两项时序断言失败，保留该失败后，在代码与测试均不变的条件下仅重跑失败任务一次，通过 `655 passed / 31 skipped / 498 subtests`。这不构成 Windows Hook 延迟上界的证明；三平台 19 项真实 SSH 验收是独立通过的记录。

本次产品补丁沿用 `release-kind=patch` 门禁，汇总十二仓正式 Release 的精确源码与基准报告。未改动组件和七大知识语料快照保留既有正式版本；历史价值评测不会重标为本次新实验。
