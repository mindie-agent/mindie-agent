**Why the report does not receive an overall scientific credibility PASS.**

1. **Its all-trial four-arm ablation claim is false.** Both DSpark G4 raw verifier results contain only `observed_cpu_ablation.full_candidate`. The DSpark verifier optionally invokes `run_ablation_suite`, does not validate its returned arms, and then sets `ablation_contract_verified=true`. The missing three arms are actual missing evidence in these runs, not just a theoretical vulnerability. See [DSpark verifier](/Users/maoxx241/code/mindie-bench/tasks/zh-vague/vllm-ascend-dspark-mtp-aclgraph-d2h-rsi-zh/verifier/verify.py:202) and [Codex DSpark raw verifier output](/Users/maoxx241/code/mindie-bench/reports/g0-g5-vllm-ascend-v2-20261103/runs/track-RSI-E2E-v4/codex/G4/vllm-ascend-dspark-mtp-aclgraph-d2h-rsi-zh_G4_1_fe375afb1030/verifier.stdout). The spatial verifier likewise can set ablation verification true even if it finds no valid ablation combination, although its retained successful v4 outputs do contain four observed arms.

2. **These are CPU contract results, not verified A5 service repairs or speedups.** The receipts explicitly say `validation_scope=controlled_cpu_tensor_and_ablation_contract`, `performance_status=unmeasured`, `native_kernel_status=unverified`, and leave NPU speedup/latency evidence null. The verifier uses Python CPU stubs for relevant native operators. The 100 percentage-point change is a change in this scoring contract’s pass rate. It cannot be interpreted as an A5 performance gain.

3. **No differential coaching is not zero coaching.** The shared L3 corpus gives task-specific Stage 1/2/3 source edits, demands three distinct candidate hashes, names the ledger and public test paths, and tells the agent to query again with `mode="reuse"` to obtain deeper specifications.
