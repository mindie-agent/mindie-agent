# MindIE Agent 工程设计原则与演进准则

[English](design-principles.en.md) · [返回文档中心](README.md)

MindIE Agent 的目标是**让通用编程 Agent 在昇腾（Ascend）NPU 与大模型推理工程中真正好用、省心、不添乱**。

在项目演进过程中，我们从最初的九项基础产品边界原则出发，结合跨平台适配（macOS / Windows / WSL）、多宿主接入（Claude Code / Codex / Kimi Code）和实机排障实践，逐步沉淀出一套完整的工程设计准则。

---

## 一、九项基础产品与工具边界原则

这九条原则定义了“什么该做成工具、什么该做成 Skill 或知识、以及如何让 Agent 少走弯路”：

1. **以完成用户目标的“总成本”衡量效率（最高准则）**
   - 成本不仅包括代码运行时间，更包括**用户的理解成本、操作步骤、等待时间、排错成本和返工成本**。
   - 任何稳定性设计只有真正降低了这些总成本才值得做；绝不能为了防范极小概率的边缘异常，给用户的每一次日常任务套上繁琐的审批或检查流程。当其他考量与本条冲突时，以本条为准。
2. **只把边界清晰的“封闭问题”做成工具**
   - 工具必须有明确的适用前提、输入输出和报错边界（例如“读取远端文件”“查询 NPU 实时状态”“给文本做隐私脱敏”）。
   - 需要结合上下文灵活判断的开放问题交给 Agent 思考；只把开放问题中反复出现、规则确定的机械动作抽成稳定工具，不为了写工具而强行揽活。
3. **绝不增加 Agent 和用户的理解负担（用户侧只留极简统一入口 `/mindie-agent`）**
   - 对用户而言，所有交互与配置都包裹在单一入口 **`/mindie-agent`** 之中——不要让用户去感知或记忆 `/mindie-agent:init`、`/mindie-agent:status` 或一长串内部参数。用户只需输入 `/mindie-agent` 加自然语言，内部状态消化与底层子命令路由完全由系统和 Agent 在后台完成。
   - 如果一个工具需要用户背诵一堆子命令、内部隐藏状态盘根错节、一旦报错还得先去翻工具源码才能搞明白怎么回事，那就是典型的反面教材。
4. **每个工具只做好一件事（单一职责边界）**
   - 一个工具聚焦解决一个或一类内聚问题。工具内部可以自动串联完成该操作所需的多个步骤，既不要把内部琐碎步骤甩给 Agent 手动拼装，也不要把毫无关系的功能塞进一个“大杂烩”工具。
5. **Skill 的核心作用是“给地图”与“渐进式披露（Progressive Disclosure）”，而不是“绑手脚”**
   - 顶层 Skill 保持极简聚焦，只呈现最核心的排查思路、知识检索与远端执行入口；低频的配置向导、历史导入、异常对账等细节放入二级参考文档（`references/`），仅在 Agent 实际遇到相关上下文时**按需渐进式披露**，绝不把大段内部运维指令一次性塞满主上下文。
   - 具体踩坑经验直接沉淀到知识库（Knowledge），不要用 Skill 强行规定死板的排查步骤。
6. **历史知识仅供参考，不具备强制权威**
   - 知识条目用普通 Markdown 记录适用条件、现象证据和局限性。检索命中或合入主干并不代表它一定适用于当前机器，切忌盲目照搬，一切以当前环境的实测现象为准。
   - Agent 按需查阅或沉淀经验，**不搞强制检索、强制写入、固定填空模板或任务结束后的汇报仪式**。
7. **按需手动唤醒知识与 Skill，默认自动触发远端执行与后台经验沉淀**
   - **领域知识与 Skill 手动按需唤醒**：遇到昇腾排障、算子适配或性能调优时，用户通过 `/mindie-agent <问题描述>` 显式唤醒知识库与 Skill 体系，平时写常规代码零打扰。
   - **`remote-dev` 默认自动触发**：日常对话中只要涉及远端服务器、容器或 NPU 操作，常驻的 `remote-dev` 工具集自动介入。
   - **经验闭环开启后每次默认自动触发**：用户在安装或首次配置时选择开启社区共享后，每次任务结束（`Stop`）时自动在后台完成脱敏与经验沉淀，**完全不需要用户在每次提问时显式叮嘱“帮我把经验沉淀下来”**。
8. **优先复用宿主、系统与成熟组件能力**
   - 只要能满足产品语义和兼容性要求，优先复用宿主自带的插件管理器、`uv` 锁定环境、操作系统原生进程管理以及已有的编译产物和验证成果。
   - 先搞清楚现有机制能做到哪一步、真实缺口在哪里，只在确有缺口的地方编写最精简的衔接代码。引入成熟方案后，及时删掉被替代的旧自研管理逻辑，不保留两套并行的状态机。
9. **工具必须透明可定位，严禁静默吞错**
   - 真实、准确、可定位地报告错误是底线要求。只要关键步骤失败了，就必须明确报错——**绝不能把读取失败伪装成“没有数据”，把配置损坏当成“首次安装”，或把本地保存成功冒充为“已发布完成”**。
   - 严格区分**已完成（completed）**、**已失败（failed）**和**外部结果不确定（unknown）**。如果主业务操作已成功、但清理或记账失败，必须分开如实报告，防止调用方误以为操作没执行而重复触发。

## 二、工程演进与运行保障准则

在实际落地过程中，围绕上述原则（尤其是第 8 条“机制复用”与第 9 条“错误可见”），我们进一步明确了五项工程执行准则：

### 10. 按真实缺口自研，彻底清理历史包袱
- **先验证再动手**：在重构更新、进程管理或 Hook 机制前，先用不消耗模型 Token 的最小实验核对宿主和操作系统原语的真实行为（包括超时、取消和异常退出表现）。
- **不维护冗余双轨**：新机制验证通过后，立即移除被替代的旧更新器、重复状态表和废弃配置，但必须妥善保留用户已有的知识正文、游标和授权设置。
- **按真实数据格式做兼容**：正式发布前不保留累赘的开发期兼容分支；正式发布后，根据实际变化的数据字段、存储 Schema 和接口契约设计兼容逻辑，不单纯拿版本号数字去猜测数据格式。

### 11. 用户授权与代码安装解耦（一次开启，后续每次默认自动生效）
- **一次配置，长期默认生效**：用户在安装或首次配置时决定的知识贡献意愿、公开目标仓库和授权项目范围属于持久化用户设置，与插件代码版本解耦。一旦开启，后续每次会话结束都会在后台自动触发脱敏采集与沉淀，无需用户在每次对话中重复说明。
- **升级不重置、不骚扰**：重启会话、重装或静默升级插件时，直接沿用已保存的授权与停用选择，绝不反复弹窗追问，也绝不把用户的“停用/暂不开启”悄悄改成开启。

### 12. 组件与插件配套发布（Paired Releases）
- **先发依赖，再发插件**：插件锁定的每一个第一方运行时组件（如 `diagnostics`、`remote-dev`、`knowledge`）都必须先在各自仓库发布正式的 GitHub Release（非 draft、非 prerelease），且 Release Tag 指向的源码 Commit、构建产物（wheel / sdist）与插件 `uv.lock` 完全一致。
- **独立版本号，按需复用**：各组件保持各自独立的版本号演进（无需为了对齐主仓库版本号而强行改号）；未发生代码变更的组件直接复用已有 Release。详见[组件与插件配套发布清单](release-compatibility-and-update.md#组件与插件配套发布)。

### 13. 后台静默更新与无感原子切换
- **兼容优先**：每个插件 Release 在 `harness-compatibility.json` 中声明经过验证的宿主版本区间，自动选择当前宿主可用的最高兼容正式版，不盲目拉取未验证的 `main` 分支。
- **热路径零阻塞**：距上次成功检查超过 24 小时后，由日常使用在后台异步触发更新检查与环境准备；日常工具调用只做极轻量的本地时间戳判断，绝不阻塞等待网络或构建。
- **空闲时原子切换**：新版本在独立目录中完成下载和 `uv` 锁定环境构建后，等待当前服务空闲时短暂获取排他锁，安全退役旧进程并原子切换安装绑定，全程无需用户确认或手动重载会话。详见[版本兼容与无感更新](release-compatibility-and-update.md)。

### 14. 故障边界与 `unknown` 外部状态保护
- **禁止静默降级**：捕获异常后如果返回空列表、跳过坏数据或退回旧缓存会改变原请求的含义，则严禁静默降级。
- **外部写操作 `unknown` 保护**：付费大模型调用或远端 Git/PR 写入一旦出现超时或回执丢失，必须记录为 `unknown`（结果不确定），绝不当作“尚未执行”去自动盲目重试；下次写入前必须先通过只读查询与远端对账。
- **协议安全不掩盖业务错误**：Hook 为了防止宿主模型死循环可以正常退出进程，但内部发生的采集或启动故障必须通过宿主支持的警告字段或下次工具调用的诊断信息清晰呈现给调用方。

## 三、开发 PR 提交前自查清单（Pre-PR Review）

MindIE Agent 旗下所有仓库的代码、配置、依赖、CI 与文档改动，在提交开发 PR 前均需对照核心原则完成自查（这是开发者的交付质量门禁，不增加终端用户的任何操作步骤）：

| 检查维度 | 自查问题 |
|---|---|
| **1. 任务总成本** | 这次改动帮用户或 Agent 省掉了什么麻烦？有没有引入不必要的后台常驻开销、重复计算或繁琐操作？ |
| **2. 工具边界** | 做成工具的逻辑是不是边界明确的封闭问题？有没有把需要灵活判断的开放问题写死成僵硬流程？ |
| **3. 认知负担** | 用户或 Agent 是否需要额外理解新的内部状态、复杂参数或管理命令？ |
| **4. 职责单一** | 模块职责是否清晰？有没有跨仓库越界、引入第二份冲突的状态表或重复编排？ |
| **5. Skill 定位** | Skill 是否保持为清晰的引导说明？有没有把提示性建议写成强制工作流？ |
| **6. 知识参考性** | 知识与反馈是否保持“仅供参考”？有没有强制要求检索、强制留存或把历史经验当成绝对权威？ |
| **7. 按需介入** | 是否做到了按需触发？有没有未经请求自动激活、跨会话串扰或强制收尾步骤？ |
| **8. 机制复用与配套** | 是否优先复用了宿主/系统/成熟组件能力？替代后旧代码是否已清理？用户数据、授权与 `unknown` 回执是否完好保留？ |
| **9. 错误可见性** | 失败路径是否真实、清晰地报错？是否存在静默吞错、假成功、对 `unknown` 写操作盲目重试，或后续清理异常覆盖主错误？ |

提交开发 PR 时，请在 PR 描述中附上简明的 `## 设计原则 Review` 小结，记录本次改动的自查结论、发现并修复的问题以及实际验证方式。
