# MindIE Agent 工程设计原则与演进准则

[English](design-principles.en.md) · [返回文档中心](README.md)

MindIE Agent 的目标是**让通用编程 Agent 在昇腾（Ascend）NPU 与大模型推理工程中真正好用、省心、不添乱**。

在项目演进过程中，我们从最初的九项基础产品边界原则出发，结合跨平台适配（macOS / Windows / WSL）、多宿主接入（Claude Code / Codex / Kimi Code / DeepSeek Harness）和实机排障实践，逐步沉淀出一套完整的工程设计准则。

---

## 一、九项基础产品与工具边界原则

这九条原则定义了“什么该做成工具、什么该做成 Skill 或知识、以及如何让 Agent 少走弯路”：

1. **以完成用户目标的“总成本”衡量效率（最高准则）**
   - 成本不仅包括代码运行时间，更包括**用户的理解成本、操作步骤、等待时间、排错成本和返工成本**。
   - 任何稳定性设计只有真正降低了这些总成本才值得做；绝不能为了防范极小概率的边缘异常，给用户的每一次日常任务套上繁琐的审批或检查流程。当其他考量与本条冲突时，以本条为准。
2. **只把边界清晰的“封闭问题”做成工具**
   - 工具必须有明确的适用前提、输入输出和报错边界（例如“读取远端文件”“查询 NPU 实时状态”“给文本做隐私脱敏”）。
   - 需要结合上下文灵活判断的开放问题交给 Agent 思考；只把开放问题中反复出现、规则确定的机械动作抽成稳定工具，不为了写工具而强行揽活。
3. **绝不增加 Agent 和用户的理解负担（用户侧只留极简统一入口 `/mindie-agent`）**
   - 对用户而言，所有交互与配置都包裹在单一入口 **`/mindie-agent`** 之中——不要让用户去感知或记忆 `/mindie-agent:init`、`/mindie-agent:status` 或一长串内部参数。用户只需输入 `/mindie-agent` 加自然语言，内部状态消化与底层子命令路由完全由系统和 Agent 在后台完成。
   - 如果一个工具需要用户背诵一堆子命令、内部隐藏状态盘根错节、一旦报错还得先去翻工具源码才能搞明白怎么回事，那就是典型的反面教材。
4. **每个工具只做好一件事（单一职责边界）**
   - 一个工具聚焦解决一个或一类内聚问题。工具内部可以自动串联完成该操作所需的多个步骤，既不要把内部琐碎步骤甩给 Agent 手动拼装，也不要把毫无关系的功能塞进一个“大杂烩”工具。
5. **Skill 的核心作用是“给地图”与“渐进式披露（Progressive Disclosure）”，而不是“绑手脚”**
   - 顶层 Skill 保持极简聚焦，只呈现最核心的排查思路、知识检索与远端执行入口；低频的配置向导、历史导入、异常对账等细节放入二级参考文档（`references/`），仅在 Agent 实际遇到相关上下文时**按需渐进式披露**，绝不把大段内部运维指令一次性塞满主上下文。
   - 具体踩坑经验直接沉淀到知识库（Knowledge），不要用 Skill 强行规定死板的排查步骤。
6. **历史知识仅供参考，不具备强制权威**
   - 知识条目用普通 Markdown 记录适用条件、现象证据和局限性。检索命中或合入主干并不代表它一定适用于当前机器，切忌盲目照搬，一切以当前环境的实测现象为准。
   - Agent 按需查阅或沉淀经验，**不搞强制检索、强制写入、固定填空模板或任务结束后的汇报仪式**。
7. **按需按会话手动唤醒知识飞轮，默认自动可用确定性工具与已激活会话后台沉淀**
   - **知识与经验飞轮按会话手动唤醒**：检索（`query`）、精读（`explain`）、反馈（`feedback`）、蒸馏（`distill`）、同步（`sync`）及后台 `Stop` 采集均需先在当前聊天显式输入一次 `/mindie-agent <问题描述>`（Codex 也接受 `$mindie-agent`），同一会话后续轮次自动沿用直至显式停用；未调用 `/mindie-agent` 的普通聊天不加载知识 Skill、不拉起知识服务、也不执行 `Stop` 采集，平时写常规代码零打扰。
   - **确定性工具默认自动可用**：日常对话中只要涉及远端服务器/容器操作（`remote-dev`）、集群探测与选卡租约（`coordinator`）、监控看板（`npu-top`）、Profiling 解析（`profiler`）、性能建模（`sim`）、本地故障诊断（`diagnostics`）或客观事实状态查询（`status`），无需输入 `/mindie-agent` 即可默认直接调用。
   - **贡献授权一次配置，在已启用会话中后台自动运行**：用户在安装或首次配置时选择开启社区共享后，授权配置跨会话持久保存；在任何已通过 `/mindie-agent` 启用的会话中，每次回合结束（`Stop`）时自动在后台完成脱敏与经验沉淀，**无需重复确认授权，也不需要用户在提问结束时专门执行收尾命令**。
8. **优先复用宿主、系统与成熟组件能力**
   - 只要能满足产品语义和兼容性要求，优先复用宿主自带的插件管理器、`uv` 锁定环境、操作系统原生进程管理以及已有的编译产物和验证成果。
   - 先搞清楚现有机制能做到哪一步、真实缺口在哪里，只在确有缺口的地方编写最精简的衔接代码。引入成熟方案后，及时删掉被替代的旧自研管理逻辑，不保留两套并行的状态机。
9. **工具必须透明可定位，严禁静默吞错**
   - 真实、准确、可定位地报告错误是底线要求。只要关键步骤失败了，就必须明确报错——**绝不能把读取失败伪装成“没有数据”，把配置损坏当成“首次安装”，或把本地保存成功冒充为“已发布完成”**。
   - 严格区分**已完成（completed）**、**已失败（failed）**和**外部结果不确定（unknown）**。如果主业务操作已成功、但清理或记账失败，必须分开如实报告，防止调用方误以为操作没执行而重复触发。

## 二、工程演进与运行保障准则

在实际落地过程中，围绕上述原则（尤其是第 8 条“机制复用”与第 9 条“错误可见”），我们进一步明确了五项工程执行准则：

### 10. 按真实缺口自研，以核心业务逻辑为唯一基准直接重构清理
- **先验证再动手**：在重构更新、进程管理或 Hook 机制前，先用不消耗模型 Token 的最小实验核对宿主和操作系统原语的真实行为（包括超时、取消和异常退出表现）。
- **以业务逻辑正确为唯一基准，直接删掉重写不合理设计**：遇到过度防御的假想敌检查、影子状态机或历史兼容包袱时，直接破坏性重构、删掉重写，不保留冗余双轨（但必须妥善保留用户已有的知识正文、游标和授权设置）。
- **按真实数据格式做兼容**：正式发布前不保留累赘的开发期兼容分支；正式发布后，根据实际变化的数据字段、存储 Schema 和接口契约设计兼容逻辑，不单纯拿版本号数字去猜测数据格式。
- **默认信任 Agent 与内部组件**：内部结果按已有契约直接消费，不因为“上游可能说错或伪造”而逐层增加证明材料、事实绑定、摘要比对或重复执行。开放判断交给 Agent，确定性计算交给对应组件。
- **本职验证做一次，下游直接复用**：精度比较、任务判分、性能测量等由负责该业务的组件完成；后续调用、提炼和报告直接使用已有结果，不维护另一套事实副本或再跑同一检查。确有新条件、实际矛盾或故障时，再定位性地补做必要检查。
- **评测问题就地修正**：判分器应按题意评价任务结果；人为改写答案的反例不自动升级为全系统防伪需求，也不成为增加运行时核验层的理由。优先投入能改善真实任务完成和经验复用的工作。

### 11. 用户授权与代码安装解耦（授权一次配置，在已启用会话中自动生效）
- **一次配置，长期持久保存**：用户在安装或首次配置时决定的知识贡献意愿、公开目标仓库和授权项目范围属于持久化用户设置，与插件代码版本解耦。一旦开启，在后续任何通过 `/mindie-agent` 启用了知识系统的会话中，回合结束时都会在后台自动触发脱敏采集与沉淀（未调用 `/mindie-agent` 的普通会话不触发采集），无需用户在每次对话中重复确认授权或下达收尾指令。
- **升级不重置、不骚扰**：重启会话、重装或静默升级插件时，直接沿用已保存的授权与停用选择，绝不反复弹窗追问，也绝不把用户的“停用/暂不开启”悄悄改成开启。

### 12. 组件与插件配套发布（Paired Releases）
- **先发依赖，再发插件**：插件锁定的每一个第一方运行时组件（如 `diagnostics`、`remote-dev`、`knowledge`、`coordinator`、`npu-top`）都必须先在各自仓库发布正式的 GitHub Release（非 draft、非 prerelease），且 Release Tag 指向的源码 Commit、构建产物（wheel / sdist）与插件 `uv.lock` 完全一致。
- **独立版本号，按需复用**：各组件保持各自独立的版本号演进（无需为了对齐主仓库版本号而强行改号）；未发生代码变更的组件直接复用已有 Release。详见[组件与插件配套发布清单](release-compatibility-and-update.md#组件与插件配套发布)。

### 13. 后台静默更新与无感原子切换
- **兼容优先**：每个插件 Release 在 `harness-compatibility.json` 中声明经过验证的宿主版本区间，自动选择当前宿主可用的最高兼容正式版，不盲目拉取未验证的 `main` 分支。
- **热路径零阻塞**：距上次成功检查超过 24 小时后，由日常使用在后台异步触发更新检查与环境准备；日常工具调用只做极轻量的本地时间戳判断，绝不阻塞等待网络或构建。
- **空闲时原子切换**：新版本在独立目录中完成下载和 `uv` 锁定环境构建后，等待当前服务空闲时短暂获取排他锁，安全退役旧进程并原子切换安装绑定，全程无需用户确认或手动重载会话。详见[版本兼容与无感更新](release-compatibility-and-update.md)。

### 14. 故障边界、禁止静默回退与 `unknown` 外部状态保护
- **严禁静默回退与吞错假成功（No Silent Fallbacks or Fake Success）**：
  - 捕获异常后如果返回 `{}`、空列表、跳过坏数据、或把失败包装成 `"status": "active"` / `exit 0` 会掩盖真实故障，则严禁静默回退；
  - **严禁次要记账反杀主结果**：当远端 NPU 命令或核心操作已经成功返回有效结果时，若本地 SQLite 回执记账或后台孙进程管道清理超时，必须保留已成功的业务结果并附加诊断告警，绝不能把已成功的业务结果覆写为 `isError = True`；
  - **警惕异常继承链误吞（如 `TimeoutError` $\subset$ `OSError`）**：在 Python 中捕获 `OSError` 前必须显式区分 `TimeoutError`，严禁自己抛出的超时异常被底层宽泛的 `except OSError:` 静默吞掉。
- **外部写操作 `unknown` 保护**：付费大模型调用或远端 Git/PR 写入一旦出现超时或回执丢失，必须记录为 `unknown`（结果不确定），绝不当作“尚未执行”去自动盲目重试；下次写入前必须先通过只读查询与远端对账。
- **协议安全不掩盖业务错误**：Hook 为了防止宿主模型死循环可以正常退出进程，但内部发生的采集或启动故障必须通过宿主支持的警告字段或下次工具调用的诊断信息清晰呈现给调用方。

### 15. 超时预算算术一致性与反“过度防御性编程”（Anti Over-Defensive Paranoia）
1. **超时预算算术铁律（Timeout Arithmetic Invariants）**：
   - **外层超时必须严格大于内层步骤与收尾宽限期之和（`outer_timeout >= sum(inner_budgets) + cleanup_grace`）**：
     - 严禁出现外层 `HOOK_TOTAL=1.5s` 包裹内层 `30s` 子命令、本地 `STOP_DRAIN (2.0s) == 远端 STOP_GRACE (2.0s)` 导致刚发 `SIGKILL` 本地就判失败、或验证器 `deadline = timeout - 0.1s` 不给 `finally: inventory()` 预留排水时间而误触发 `UnknownExternalEffects` 等算术倒挂；
     - 多阶段故障诊断（如 Stage 1 含 SSH ControlMaster 与 Stage 2 绕过 ControlMaster）必须分配独立预算，严禁 Stage 1 耗尽 100% 共享 `deadline` 导致 Stage 2 永不可达；
     - 严禁在 Shell 中写 `timeout 10 cmd || cmd`（当 `timeout` 以退出码 `124` 超时退出时，`||` 会立即执行不带 `timeout` 的裸命令导致永久挂死）。
   - **消灭两极化超时（告别毫秒级误杀与 `timeout=None` 无限裸奔）**：
     - **禁止热路径亚秒级（`< 1s`）SQLite 锁超时**：多线程/跨进程 SQLite 写锁严禁设 `100ms~250ms` 微超时（会在正常索引/分块写入时误杀请求或永久丢弃 Stop 会话），统一开启 WAL 模式并设置 `3.0s~5.0s` 合理等待；
     - **禁止外部子进程与网络握手 `timeout=None`**：所有外部子进程（`gitleaks`、摘要模型、候选版本验证、全局 `flock` 内的 `docker inspect/top`）必须设置显式有界超时；RPC 握手等待（如 `ready.wait`）必须在函数入口即纳入 `deadline` 约束。
2. **反过度防御性编程四大铁律（以核心业务逻辑为基准，剥离防御性假想敌累赘）**：
   - **铁律一：本地状态轻量建连，禁止每条 SQL 热路径 `.owner`/Schema 反射自检**：SQLite 仅在 `open_database` 时执行 `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;` 与表结构初始化，严禁在每次 `SELECT` 上拦截跑 `lstat(.owner)` 或 `:memory:` 全表反射。
   - **铁律二：严守外部副作用与本地状态边界，废除本地单向自锁死（Self-Bricking）**：仅对不可逆外部写操作（计费 LLM、GitHub PR/Issue、远端破坏性写）保留 `unknown` 回执对账；本地幂等状态（虚拟环境升级、`consent.json` 迁移、容器 `task_environment` 准备）遇到异常必须透明报错并支持下次无锁时幂等自愈，严禁写入 `suppressed` / 永久 `fault` / `TaskRootBusy` 自锁死墓碑。
   - **铁律三：禁止跨仓复制粘贴 `*_fallback.py` / `*_bootstrap.py` 影子状态机与 `ctypes` Win32 ACL 繁文缛节**：宿主插件直接依赖由 `uv.lock` 锁定的共享组件，文件原子替换统一使用标准库 `os.replace()`。
   - **铁律四：禁止 `inspect.signature` 内部函数签名反射锁死与巨型字符串内嵌 Python 代码（如 `REMOTE_FILE_PY`）**：探针只验公开接口与版本契约；远端 worker 必须作为独立 `.py` 模块维护。

### 16. 测试设计准则：杜绝凑数测试，拥抱常备 A2/A3 NPU 真机分层验证
完整规范见[分级测试体系与用例设计规范](testing-architecture.md)：
1. **用例有效性红线（Every Test Must Earn Its Keep）**：
   - **严禁防御性偏执凑数与文本匹配测试**：严禁编写纯粹验证 Python 类型检查/防御性 `ValueError` 分支、反复测试 `chmod 0o777`/`symlink` 假想敌、核对静态常量/枚举字符串列表、或者用正则去 grep `README.md`/`SKILL.md` 文案的“凑数测试”；
   - **严禁测试替静默吞错背书**：严禁编写“当底层报错或超时时，断言返回 `exit 0` / `{}` / `"active"`”的假阳性测试；
   - **严禁失真造假**：严禁在集成测试中动态覆写生产脚本文件（如用假脚本替换 `admission_ops.py`）或伪造与真实服务端字段不符的 `MagicMock`。
2. **四级测试金字塔（Tier 0 ~ Tier 3，默认常备 A2/A3 昇腾 NPU 环境）**：
   - **Tier 0（纯内存核心逻辑单测，`< 5s`）**：零外部子进程、零网络、零 `sleep`，覆盖解析器（基于真实 A2 910B / A3 910C / A5 硬件 Golden Captures）、状态机流转（`InMemoryHostQueue` 等真实内存回路）、脱敏规则、领域检索召回质量与协议转换。
   - **Tier 1（本地组件契约与进程边界测试，`< 15s`）**：复用 Session 级预构建 Git/SQLite 模板，验证跨进程锁、`python -I` 真实隔离启动、毫秒级可注入超时回收（严禁在测试内联网 `pip install` 或跑 10MB 级 `fsync` 轰炸）。
   - **Tier 2（常备 A2/A3 NPU 真机无损集成测试 `@pytest.mark.live_npu`，`< 25s`）**：直接连接常驻 A2 (`173.125.1.2`) 与 A3 (`192.168.13.165` / `.156` / `.154`) 集群，使用隔离沙箱目录（如 `state_dir="/tmp/mindie-npu-test-<uuid>"`）在不干扰线上任务的前提下，常态化验证真机 `npu-smi` 探测、多 Die `Phy-ID` 映射、Docker 容器穿透、Linux `/proc` 进程树排空与租约防抢占。
   - **Tier 3（端到端宿主 CLI 与 `mindie-bench` 实机基准验收，`< 90s`）**：驱动真实宿主 CLI 与 `mindie-bench` Canary 任务完成闭环验证。

### 17. Agent-Native 代码与注释规范（100% Agent 维护代码库）
MindIE Agent 旗下全部代码与知识仓库均为 **100% 由编程 Agent 阅读、演进与维护的代码库**。代码结构与注释必须针对 Agent 的注意力机制与工具窗口（如单次 `view_file` 800 行上限）做原生优化：
1. **模块体量与上下文窗口友好性（Context-Window Friendliness）**：
   - 核心业务模块应保持高内聚、精炼紧凑，原则上单文件控制在 **800 行以内**（单次 `view_file` 即可完整加载全貌），避免因防御性样板代码膨胀导致 Agent 被迫多次翻页切片阅读；
   - **严禁 5~6 层子进程蹦床（Subprocess Trampolines）与多层透传包装**：调用链必须扁平直观，确保 Agent 在 1~2 次文件读取内即可看清从入口到核心执行的完整闭环。
2. **强制模块顶部契约头（Module-Top Agent Invariant Header）**：
   - 每个核心业务模块文件顶部（前 30 行 Docstring 内）必须包含标准化的四段式契约声明，让 Agent 无需通读数百行实现即可瞬间掌握模块边界：
     - `[Role]`：一句话明确该模块的单一职责与核心入口；
     - `[Invariants]`：该模块必须死守的核心业务不变量（如状态机合法流转、缺失数据返回 `None` 而非填 `0`、禁止静默吞错）；
     - `[Timeouts & Locks]`：该模块涉及的锁粒度、SQLite/文件锁策略与内外层超时算术关系（`outer_timeout >= sum(inner_budgets) + cleanup_grace`）；
     - `[Side-Effect Policy]`：外部副作用边界（纯内存计算、幂等本地状态自愈、或需记录 `unknown` 回执的不可逆外部写入）。
3. **注释原则：写清“业务不变量与硬件/协议边界（Why & Invariants）”，严禁为过度防御写借口**：
   - **必须写注释的地方**：非显而易见的昇腾硬件行为（如 A3 910C 双 Die 拓扑下 `8 NPU × 2 Die = Phy-ID 0..15` 映射规则）、跨进程/容器协议边界（如 Linux `/proc` 跨容器 PID 命名空间排空、`SIGTERM -> SIGKILL` 排水宽限期算术）、以及核心领域不变量；
   - **严禁写注释的地方**：严禁复述代码字面意思，严禁编写长篇大论替“假想敌防御分支”“冗余兜底状态”找合理化借口（遇到需要靠大段注释辩解的防御性累赘代码，应直接连代码带注释一并删掉重写）。

### 18. 编码性能、内存/显存有界性与本地/远端规格分流准则（Bounded Memory/VRAM & Spec-Driven Placement）
详见[执行资源预期与本地/远端规格匹配设计](execution-resource-budget-design.md)。所有组件代码在设计阶段即必须对计算耗时（影响超时）、内存（影响本机死机）与显存（影响炸卡）负责，严禁编写一出问题就靠堆砌大机器掩盖的粗放实现：
1. **内存工作集有界铁律（$O(\text{Active State})$ 而非 $O(\text{Total History})$）**：
   - **状态与历史解耦**：模拟器（`sim`）、性能分析器（`profiler`）、诊断采集（`diagnostics`）在主循环中，常驻内存只能与**当前活跃状态（Active Batch / 当前时间窗）**成正比，**严禁随总迭代步数（$T$）、总生成 Token 数或日志总行数做无界累加（如 `history.append` 全量快照）**；
   - **在线增量聚合与有界滑窗**：吞吐、分位数（P50/P90/P99）、算子耗时汇总在循环内增量计算；确需保留明细事件时必须使用**显式有界环形缓冲区（Ring Buffer / Top-K）或边算边流式落盘（JSONL Streaming）**，用完即释放引用；
   - **大文件禁止全量读入内存**：读取超过 **`50 MB`** 的 Profiling Trace、日志或索引文件时，严禁直接 `json.load()` / `file.read()` 全量展开为庞大对象图，必须采用流式扫描（分块读取 / 行迭代 / `mmap` / SQLite 索引）。
2. **量化内存红线与算法性能纪律（`1 GiB` 缺陷警戒线）**：
   - **控制面与分析组件体量基线**：常规工具调用与分析任务（`sim` 仿真、`profiler` 汇总、`knowledge` 检索、`coordinator` 调度）单进程工作集增量应控制在 **`<= 256 MiB`（峰值 `<= 512 MiB`）**。除真正加载大模型权重或 C++ 大型并行链接外，任何 Python 组件单进程峰值内存超过 **`1 GiB`** 默认视为**算法或数据结构缺陷（Bug）**，必须重构代码（如使用 `__slots__`、数组、流式处理），严禁靠调大机器限额放行；
   - **消灭三大超时与内存膨胀反模式**：（1）严禁在解释器热循环内跑 `copy.deepcopy`、调用外部子进程（`subprocess.run`）或逐行 `sqlite.commit()`；（2）模拟器遇到同质重复阶段应采用解析跳步/批折叠（Event-Driven Jump）代替逐拍空转；（3）并行 Worker 数必须受 CPU 与可用内存双重约束：$\text{Workers} = \max(1, \min(\text{可用 CPU 核数}, \lfloor \text{可用安全内存} / \text{单 Worker 峰值内存} \rfloor))$，严禁无脑 `os.cpu_count()`。
3. **显存（HBM / VRAM）安全铁律：“零权重控制面”与“先算账、后上卡”**：
   - **控制与分析路径零权重、零设备上下文**：仅需读取模型结构（层数、Hidden Size、词表大小）或算子签名时，只允许解析 `config.json` 或 `safetensors` 文件头（前 8 字节 + JSON Header），**严禁为了读元数据而加载权重文件或 `import torch_npu` 初始化设备上下文**；
   - **上卡前静态显存预算核验（Pre-Flight VRAM Sizing）**：真正占用 NPU/GPU 的操作（模型服务、算子压测、`mindie-bench`）在启动前必须核算 $\text{Expected VRAM} = \text{权重} + \text{KV Cache} + \text{激活峰值} + \text{HCCL 通信 Buffer} + \text{Runtime 预留}$，并核对目标卡实际空闲显存（`vram_free_mb >= Expected VRAM`，A3 910C 按单 Die 物理边界核算），不满足时在启动前拦截或重选节点，严禁盲目拉起进程等 OOM 炸卡。
4. **跨平台（Windows / macOS / Linux）按真实规格分流，严禁按操作系统硬编码**：
   - **禁止写死 `sys.platform == "darwin"` 或 `os.name == "nt"` 决定能否运行**：MindIE Agent 同时服务 Windows、macOS 与 Linux 用户；
   - **声明资源预期（`WorkloadExpectation`）并与真实机器规格（`HostHardwareSpec`）匹配**：重计算/重内存/需显存的操作在启动前声明 `{cpu_cores, memory_mb, vram_mb, expected_seconds}`，由执行层统一对比**本机（Windows/macOS/Linux）**与**远端服务器（`fleet_probe.py`）**的真实可用规格——**本机规格充裕（包括高配本地工作站规格大于服务器时）直接本地执行并按本机算力自适应并发度与超时；本机规格不足则启动前自动分流至匹配的远端服务器**。

## 三、开发 PR 提交前自查清单（Pre-PR Review）

MindIE Agent 旗下所有仓库的代码、配置、依赖、CI 与文档改动，在提交开发 PR 前均需对照核心原则完成自查（这是开发者的交付质量门禁，不增加终端用户的任何操作步骤）：

| 检查维度 | 自查问题 |
|---|---|
| **1. 任务总成本** | 这次改动帮用户或 Agent 省掉了什么麻烦？有没有引入不必要的后台常驻开销、重复全量哈希/IO 校验或繁琐操作？ |
| **2. 工具边界** | 做成工具的逻辑是不是边界明确的封闭问题？有没有把需要灵活判断的开放问题写死成僵硬流程？ |
| **3. 认知负担** | 用户或 Agent 是否需要额外理解新的内部状态、复杂参数或管理命令？ |
| **4. 职责单一** | 模块职责是否清晰？有没有跨仓库越界、引入第二份冲突的状态表或复制粘贴 `*_fallback.py`/`*_bootstrap.py` 影子状态机？ |
| **5. Skill 定位** | Skill 是否保持为清晰的引导说明？有没有把提示性建议写成强制工作流？ |
| **6. 知识参考性** | 知识与反馈是否保持“仅供参考”？有没有强制要求检索、强制留存或把历史经验当成绝对权威？ |
| **7. 按需介入** | 是否做到了按需触发？有没有未经请求自动激活、跨会话串扰或强制收尾步骤？ |
| **8. 机制复用与配套** | 是否优先复用了宿主/系统/成熟组件能力？替代后旧代码是否已直接删掉重写？用户数据、授权与外部副作用 `unknown` 回执是否完好保留？ |
| **9. 错误可见性与反静默回退** | 失败路径是否真实、清晰地报错？是否存在 `except Exception:` 静默吞错返回 `{}` / `"active"` / `exit 0` 假成功、Python `except OSError:` 误吞 `TimeoutError`、对 `unknown` 写操作盲目重试，或因本地记账/清理超时反杀已成功的远端主结果？ |
| **10. 超时预算与算术一致性** | 新增或修改的超时是否满足**“外层预算 ≥ 内层步骤总和 + 收尾排水宽限期（如 `SIGTERM->SIGKILL` / `inventory`）”**？是否消除了热路径亚秒级（`<1s`）SQLite 锁误杀、外部子进程 `timeout=None` 无限等待、握手脱离 `deadline` 以及 `timeout N cmd \|\| cmd` 超时二次裸跑？ |
| **11. 反过度防御性编程（四大铁律）** | 是否严格遵守反过度防御四大铁律：（1）零热路径 SQL `.owner`/Schema 反射自检；（2）仅不可逆外部写用 `unknown`，本地状态零单向自锁死（无永久 `fault`/`suppressed`/`TaskRootBusy`）；（3）零跨仓复制 `*_fallback.py`/`*_bootstrap.py` 与 Win32 ACL 繁文缛节（统一 `os.replace()`）；（4）零 `inspect.signature` 内部签名锁死与巨型内嵌 Python 字符串（远端 worker 独立 `.py` 模块）？ |
| **12. 分级测试有效性** | 新增测试是否验证真实核心业务与领域质量，而非测防御性 `chmod`/`symlink`/`ValueError` 假想敌、替静默吞错背书、覆写生产脚本或 grep 文档？测试是否通过 `conftest.py` / 临时目录严格隔离 `MINDIE_DIAGNOSTICS_ROOT`、`MINDIE_DIAGNOSTICS_CONFIG` 与 `$HOME`（零污染宿主机 `~/.local`、`~/.config` 或系统级 LaunchAgent/systemd 服务）？是否符合 Tier 0 (`<5s`) ~ Tier 3 耗时预算与常备 A2/A3 真机无损验证要求？ |
| **13. Agent-Native 代码与注释规范** | 核心模块是否保持精炼（单次 `view_file` 800 行友好、无多层子进程蹦床）并在顶部前 30 行声明 `[Role]`/`[Invariants]`/`[Timeouts & Locks]`/`[Side-Effect Policy]` 契约头？注释是否聚焦业务不变量与硬件/协议边界（如 A3 双 Die `Phy-ID`），而非替防御性假想敌代码写借口？ |
| **14. 性能、内存/显存有界性与规格分流** | 内存工作集是否严格保持 $O(\text{活跃状态})$ 而非无界累加全量历史或一次性展开 `>50MB` 大文件（控制/分析组件单进程常规峰值 `<= 512 MiB`，严禁 `> 1 GiB` 膨胀）？热循环内是否消除了 `deepcopy`/起子进程/逐行 Commit？并发 Worker 数是否同时受可用内存与核数约束？控制面是否保持零权重/零设备上下文，且重计算或显存（HBM/VRAM）操作在启动前按 Windows/macOS/Linux 本机与远端的真实规格自动分流（无 `sys.platform` 硬编码特判）？ |
| **15. 自动更新就绪必检与行尾规范** | 涉及知识库单元、共享组件、宿主插件或 `channels/0.1.json` 变更时，是否通过了 `python3 .github/scripts/check_auto_update_readiness.py --require-siblings --verify-local-hosts`（确保分级知识单元 `revision` 单调递增、`publication-contract.json` 与 `verified_commit` 对齐、且 `harness-compatibility.json` 覆盖当前活跃宿主 CLI 版本）与 `python3 .github/scripts/check_lf_eol.py`（全仓文本文件统一 Unix `LF` `\n`）？ |

提交开发 PR 时，必须在 PR 描述中完整勾选并填写 [`.github/pull_request_template.md`](../.github/pull_request_template.md)（包含 `## 变更摘要 (Summary)`、全部勾选的 `## 设计原则 Review (Pre-PR Checklist)` + 具体 `自查结论与证据`、以及 `## 验证结果 (Verification)`）。CI 门禁工作流（`.github/workflows/pr-checklist.yml` + `.github/scripts/check_pr_checklist.py`）会在每次 PR 创建/编辑/同步时自动核验，未完成勾选或未填写实质自查与验证证据的 PR 将被 CI 拦截禁止合入。
