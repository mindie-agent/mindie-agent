# MindIE Agent 设计原则

Status: current

MindIE Agent 完整继承 VAWS 的以下九条设计原则。产品更名、Plugin 形态、共享组件和各 Harness 适配均受同一组原则约束；本轮重构不另设替代原则，也不把实现细节提升为新的强制流程。VAWS 的旧运行入口退役，不改变这些原则的有效性。

这些原则用于 MindIE Agent 的设计取舍。第 1 条优先于其他设计选择，但降低成本不能成为隐藏错误或降低已确认产品要求的理由。现有组件、接口、Skill、文档和此前的方案均可据此调整。普通业务任务仍按需使用能力；所有开发任务在提交 PR 前必须完成本文规定的设计原则 review。这是开发交付要求，不增加用户审批步骤。

1. **以完成用户实际目标的总成本衡量 Agent 效率。** 成本包括理解、操作、等待、排错和返工。稳定性只有在降低这些成本时才值得投入，不能为了覆盖小概率异常，让每次普通任务都承担复杂流程。当其他设计与此冲突时，以此条为准。
2. **只将边界明确的封闭问题工具化。** 工具的适用条件、输入输出和失败边界需要明确。情况多变、依赖上下文判断的问题，优先考虑其他方式。开放问题中反复出现、边界已经明确的机械操作，可以抽取为稳定工具；不为了写工具而扩大职责。复杂程度或能否写成代码，本身都不能判断一个问题是否封闭。
3. **不能增加 Agent 的理解负担。** 工具应消化内部管理复杂度，让 Agent 用任务所需概念完成操作。参数众多、隐藏状态复杂、出错后必须学习实现才能定位的 CLI，是典型负例。
4. **每个工具有明确的边界和定义。** 核心解决一个问题或一类问题。可以在内部完成兑现该操作所需的多个步骤；不把内部每一步都交给 Agent 编排，也不把其他职责塞进一个大而全的工具。
5. **Skill 主要提供信息。** 提供适用场景、能力入口、必要示例和可选方法，帮助 Agent 判断。可由知识条目承载的经验直接沉淀为知识，不用 Skill 强制规定研究路线。基本用法应在入口可得，避免为拼出一次调用而反复检索。
6. **知识仅供参考。** 用普通 Markdown 保留适用条件、证据和不确定性；检索命中、审核或发布不赋予其决策权威。决策以当前现象和分析为主。Agent 按需查阅或留存，不承担必查、必写、固定格式或额外收尾流程；可按相关性、时效性和验证成本复用知识，无需每次从零重证。
7. **所有工具和 Skill 按需介入。** 普通 PR review、远端目录查看与从零开发模型都可以在 MindIE Agent 中完成。轻量任务直接使用相应原生能力；重型任务按实际需要组合能力，使用工作区本身不触发整套流程。
8. **尽量复用已有有效成果。** 在满足当前任务语义和兼容条件的前提下，复用已有算子、编译产物、环境及其他有效成果。检查与变化范围相称，避免重复全量验证。常规检查由工具内部完成，必要的复用依据、失效与失败原因仍可查询。
9. **工具可观察、可定位，禁止隐藏错误。** 正确、真实、可定位地报告错误是产品要求。必要步骤未完成时，不能把结果报告成成功、空结果、首次使用、用户停用或已完成的降级产物；不能擅自把必要能力变成可选能力。明确区分已完成、失败和结果不确定，说明失败阶段、已知原因及受影响范围。业务操作已完成而记录结果失败时，分别报告两者，不诱导重复执行。超出能力范围时，把事实交还 Agent；不能让 Agent 为解开黑盒而被迫学习整个内部实现。

这些原则不预先决定包的数量、命令的数量、必须有多强的 session，或是否建立统一 Core。具体方案需要说明它减少了哪种已经发生或有依据的任务成本。已有正确实现和有效验证证据也是可复用成果。

当前产品边界见[架构](architecture.md)，知识流程见[Transcript 复用架构](transcript-reuse-architecture-2026-10-04.md)，授权和更新见[Harness 生命周期](harness-boundary-and-lifecycle.md)，实际完成情况见[统一实施进度](implementation-status.md)。

限制应说明它防止的具体故障，并作用于对应操作。一次调用不自动重试，不等于永久停止后续正常检查；开始过不等于完成；运行参数不等于兼容协议。不要把验收时的次数、截止时间或样本数量直接变成产品门槛。

## 第 9 条的执行约束：禁止隐藏错误

以下是必须遵守的失败语义，不是可选的健壮性建议：

- **不伪造完成。** 读取失败不是“没有数据”，损坏配置不是“首次使用”，后台进程存活不是“必要 worker 正常”，本地保存成功不是“整理或发布成功”。任一必要步骤失败，整体结果必须明确报告失败、部分完成或结果不确定，不能无条件返回成功。
- **错误必须到达调用者。** 报告失败的操作和阶段、已知原因、已完成与未完成的部分，以及是否存在结果不确定的外部副作用。原因未知时明确写未知；保留主错误及必要的脱敏定位信息，不用空值、默认值、通用成功回执或仅后台日志替代错误结果。秘密和原始私有内容不得写入公开错误信息。
- **禁止静默降级。** 捕获异常后返回空集合、跳过坏记录、换成摘录、禁用必要功能、启用备用状态库或使用旧缓存，都必须检查是否改变原请求的含义。仅在仍兑现原请求，或用户已明确允许相应降级时使用替代路径，并说明原因、实际结果和未完成部分。不得把过期缓存标成刷新成功，不得把未经必要处理的产物标成最终产物。
- **保留实际执行结果。** 操作成功而记账、清理或诊断失败，必须分别说明；后续异常不能覆盖原始错误，也不能让调用者误以为业务操作未发生。外部写入结果不确定时明确报告不确定，先核对原操作，不能当成“尚未执行”自动重试。
- **协议保护不等于业务成功。** Hook 或协议包装层可以为防止模型续跑而正常结束，但其内部业务失败仍须通过调用者可见的状态或错误提示报告。必要 worker 退出、必要依赖缺失和异步处理失败不能因前台已返回或进程仍存活而消失。
- **验证失败分支。** 对本次改动涉及的异常处理检查实际返回结果和副作用；必要时用故障注入验证没有错误地推进游标、发布残缺产物、丢弃状态或重做写入。正常的未启用、无匹配结果、重复事件和预期资源清理应与故障明确区分。验证范围与改动相称，不建立无关的全量验收流程或正文历史档案。

## 开发 PR 的必做 review

本要求适用于 MindIE Agent 所有仓库的所有开发任务，包括功能、修复、重构、配置、依赖、构建/CI 和项目文档变更。纯知识内容或使用反馈贡献继续按内容规则处理；不能因此把知识采集、整理、发布等功能开发排除在本要求之外。

**创建任何开发 PR（包括 draft）之前，任务执行者必须读取当前设计原则，针对最终 diff 及其影响路径逐条审查全部九条原则。** 测试通过、CI 通过、已有实现如此或勾选模板，均不能代替这次 review。读不到原则或未完成审查时必须明确报告，不得提交开发 PR，也不能声称已审查。PR 更新产生新变更后，提交更新前复查受影响的原则并更新审查依据。

| 原则 | 必须回答的审查问题 |
|---|---|
| 1 总成本 | 改动减少了什么实际成本？是否增加无依据的常驻工作、重复计算、存储、恢复流程或用户操作？ |
| 2 封闭问题 | 工具化的问题是否边界明确？是否把需要判断的开放问题固化成机械流程？ |
| 3 理解负担 | 用户或 Agent 是否被迫理解更多内部状态、参数或管理步骤？ |
| 4 单一边界 | 能力职责是否明确？是否越过组件边界、引入第二权威状态或重复编排？ |
| 5 Skill 信息性 | 是否把提示性信息变成强制工作流？是否用 Skill 承担应由知识或工具承担的职责？ |
| 6 知识参考性 | 是否把经验或反馈当成权威或认证？是否强制查阅、留存或虚构证据？ |
| 7 按需介入 | 是否出现未经请求的激活、跨 session 使用、额外模型调用或强制收尾？ |
| 8 成果复用 | 是否重复已有实现、重新处理未变材料、重复运行无关验证或丢弃仍有效成果？ |
| 9 错误可见 | 所有受影响失败路径是否真实报错？是否存在静默 fallback、假成功、结果不确定时重试或主错误被覆盖？ |

审查发现违反原则的问题，必须修正并复查后再提交；不能把它留给后续 reviewer，或用“兼容”“防御性编程”“可选能力”作为未经论证的豁免。确实不适用的原则应依据本次 diff 简述原因，不能用整组 N/A 跳过审查。外部环境尚未验证的部分明确列为未验证，不写成通过；这不要求为无关变更重做全部实机验收。

PR 描述必须保留简短、具体的“设计原则 Review”记录：审查覆盖的提交和原则文档版本、九条原则的结论及适用性依据、发现及修正的问题、实际验证和未验证边界。内容可以合并表述，但不能只写“已遵循全部原则”。后续 reviewer 同样按这些原则复核实际 diff；审查记录不能代替代码审查，也不新增一轮用户授权。
